## 已确认 Q-001

Windows XP 与 CentOS 7 对首个发布版本属于硬性发布门槛、分级门槛，还是后续兼容目标？

结论：两者都是硬性发布门槛。参考目标为 Windows XP SP3 x86 与 CentOS 7 x86_64。

## 已确认 Q-002

旧 macOS 应属于硬性发布门槛、设计兼容但非发布门槛，还是明确不支持？如果是硬门槛，下一步再确定最低系统版本与 CPU 架构。

结论：v0.1 不承诺旧 macOS，当前只考虑旧 Windows 与旧 Linux 的专门兼容性。

## 已确认 Q-003

现代 Windows 与现代 Linux 应属于同等硬性发布门槛、基础冒烟验证，还是首版不建立正式承诺？

原结论后来由 D-012 修订：Windows 客户端矩阵包含 XP SP3、Vista SP2、7 SP1、8、8.1、10、11；所有最终声明支持的平台都执行完整测试，不设置只冒烟的支持层。Linux 的具体测试发行版以后确认。

## 已确认 Q-004

Windows 发布物采用一套贯穿 XP 至 11 的 x86 构建，还是为现代 x64 系统额外提供原生 x64 构建？

结论：Windows 只提供 Win32 x86 32 位构建，不提供原生 x64 或 ARM 构建。

## 已确认 Q-005

Linux 发布物也只支持 x86 32 位，还是保留当前 CentOS 7 / Debian 13 x86_64 目标？

结论：Linux 只支持 x86_64，不发布 i686 或 ARM 版本。原问题中的具体发行版清单后来依 D-012 延后确认。

## 已确认 Q-012

AgentLoop 的“完成权”归谁：模型无工具调用即直接结束，Runtime 依据工具配对、验证、预算、防卡死和 stop hook 的结构化事实决定，还是每次由独立评估器裁定？

结论：正常完成由主模型主导。问题标题中的“无工具调用即直接结束”是早期候选代理，未被确认为可靠 signal；普通无工具回复也可能是提问、部分进展或拒绝，typed finish/ask-user 仍由 `AQ-251`、`AQ-252` 决定。原结论曾增加独立“使用终止评估器”开关；该配置面已由 D-027 正式取代：当前有效 `DoubleCheck` 开启时，在明确 finish 后单独发起完成复核请求，关闭时不复核。Runtime 仍负责如实标记取消、硬预算、未收口工具和基础设施错误，不把这些情况改写成正常完成。

## 前提已由 D-027 修订、控制流待决 Q-013

启用终止评估器后，如果评估器认为“现在不应终止”，AgentLoop 应怎样继续：把评估意见交还主模型并在同一 turn 继续、结束当前 turn 后开启纠正 turn，还是停止并等待用户决定？

当前推荐把结构化评估意见交还主模型，在同一 turn 内继续，但必须增加评估次数上限，避免“主模型要求终止—评估器拒绝”的无限循环。

综合决策包 B-08 的回复已经修订了本题前提，并由 D-027 正式归档：终止复核不再作为与 `DoubleCheck` 正交的独立用户开关；开启 `DoubleCheck` 时包含结束复核，关闭时没有结束复核。项目负责人同时给出该模式的定位：花费更多时间和 Token，换取更多安全。

这项回复尚未完成正式归档。评估拒绝后是否在同一 turn 继续、使用哪个模型、输入范围、失败/超时降级及次数/费用/墙钟上限仍是待决子契约，见下文 `AQ-019` 至 `AQ-023`、`AQ-109`。在这些子契约确认前，不能把原先的推荐控制流自动视为已确认。

## 已确认 Q-014

上下文 hash 按当前逻辑文件路径实时计算，因此重命名 `我的任务.xml` 会得到新的 hash。这个 hash 是允许随路径变化的查找别名，还是必须成为重命名后也不变的会话主身份？

结论：不建立永久 `ContextId`。当前逻辑 XML 路径是当前地址，固定 16 位 hash 由它在运行时计算；名称或路径变化后 hash 重新计算，旧 hash 立即失效。XML 内部事件关系另由局部序号/schema 表达，不能把路径 hash 当成跨重命名外键。

## 已确认 Q-015

当 `yaca --continue X` 等通用解析入口收到选择器时，怎样同时满足“由当前目录向外搜索”“名称/hash 语义可解释”和“尽量少遍历旧磁盘”？

三种方案是：严格先完整扫名称、未找到再完整扫 hash；对 16 位输入先按 hash 并允许提前返回；或使用互不重叠的增量搜索环，在每个环中单遍同时收集名称/hash 命中，完成本环后再按规定优先级裁决。

结论：采用第三种，并正式确定“距离优先、同一搜索环名称优先于 hash”。计算层见到合法 16 位 token 后同步计算 hash，不把目录树完整扫两遍；语义层在本环完成必要扫描后先处理名称结果。最先产生可裁决结果的搜索环获胜，因此近层 hash 先于远层名称，且不继续扫描外层排查全局碰撞。每个 XML 候选最多探测和匹配一次，结果不依赖文件系统枚举顺序；若本环的必要扫描不完整，则不能把已观察到的单个命中宣称为唯一，也不能越过本环连接更远结果。

## 完整性审阅方法

题库不以“想到多少功能名”为完整标准，而对每项能力交叉检查五个维度：

1. **生命周期**：安装/解压、无配置启动、创建会话、一次 turn、工具副作用、取消、异常退出、恢复、重命名/迁移、压缩、升级和卸载。
2. **参与者**：用户、主模型、完成复核模型、工具/子进程、TUI/CLI、宿主操作系统、第三方 XML reader、测试与维护者。
3. **状态与边界**：INI、当前 XML、运行时内存、工作区、外部网络/进程；谁拥有状态、何时 durable、能否取消、失败后谁恢复。
4. **失败类型**：无效输入、部分响应、超时、取消、磁盘满、崩溃、并发外改、权限拒绝、旧版本/未知字段和目标平台能力缺失。
5. **用户可见面**：chat、各 REPL、help、审批、错误、恢复、导入导出、self-test 和发行 zip；同一领域结果不能因入口不同而改变。

每个高风险决定最终都必须能回答六句话：谁决定、依据什么、何时落盘、怎样取消、失败后是什么真实状态、用户和测试怎样看见证据。`DESIGN-CHECKLIST.md` 保留 354 个主题级检查点；下面的 AQ 是原子分支与技术证明点，其中真正改变产品边界的内容由决策包交给负责人，其余由规格/原型证明，两者不是用数字互相替代。

## 第一、二轮已经发现的十五个矛盾

下面保留早期审计结果；第三轮新增的 typed finish、事件泵、raw shell 权限、外来 XML 信任、Key 生命周期、单 XML 性能和 undo 范围等高风险项见 `AQ-251` 至 `AQ-360`；第四轮新增的运行时外改、Model scheduler、ask-user/retry、draft/details、管理事务、文件系统与扩展关闭边界见 `AQ-361` 至 `AQ-373` 和 [`ARCHITECTURE-READINESS.md`](ARCHITECTURE-READINESS.md)。

1. `Alt+Enter` 在旧 Windows 控制台可能被系统占用；`Ctrl+Enter`、`Shift+Enter` 在 cooked line 输入中也不能可靠区分。必须决定 native/raw 输入还是点命令后备。
2. “内部只使用 ASCII”不能等于“拒绝非 ASCII 用户数据”，否则已确认的中文上下文名和 CJK 路径失效。建议限定为代码标识、配置键、机器字段和 UI 固定文字使用 ASCII；用户路径、对话和 XML 内容仍为 UTF-8。
3. “配置损坏就无法启动”与“self-test 用于检查配置”存在入口矛盾。需要明确 self-test 是否也必须先通过完整配置加载。
4. “文件只有 INI/XML”与锁、临时提交、迁移备份、崩溃恢复和诊断日志存在物理冲突。应明确是长期用户数据格式只有 INI/XML，还是字面上禁止任何辅助文件。
5. 明文 Key 已选，但复制 XML 到另一台机器不能同时带走模型凭据；“完整接盘”必须定义为需要目标机器重新提供匹配 Model 配置。
6. 自定义 XML 不会天然被 Codex、CodeWhale 等项目读取。可以承诺信息充分且提供公开 schema/导出，不能承诺第三方无需适配即可原生续接。
7. “相信模型、使用原始工具”不能取消 tool schema、operation ID、结果配对和权限入口，否则 AgentLoop 无法恢复。
8. `DoubleCheck` 已被要求包含终止复核，需正式替代此前“可能正交”的候选说明。
9. 项目负责人选择配置顺序决定默认模型/权限，应撤回显式 Default ID 推荐，并定义重排、禁用第一项和重复 section 的行为。
10. “不需要消歧前缀”不等于允许碰撞时任取；同名或 hash 碰撞仍必须返回歧义错误或交互候选。
11. “不提供显示模式切换”可以成立，但运行时仍必须自动降级颜色、按键和光标能力。
12. 路径以 `-` 开头时，双引号由 shell 处理，不能阻止 CLI 把它解析成选项；仍需要 `--` 或明确参数位置。
13. 只有 XML/INI 时，配置尚未加载前、上下文尚未创建前的崩溃诊断放在哪里仍未定义。
14. self-test 第三阶段用 LLM 判断“Yolo 却只读”等名称语义只能作为建议，不能把命名风格当作配置正确性的硬证据。
15. 上下文超限时可以推荐更大上下文模型，但自动切换会改变费用、协议和隐私；建议只提示，不自动切换。

## P0：跨系统高杠杆原子问题

### Prompt、人格与指令

#### AQ-001 Prompt 权威链

状态：部分。依赖：B-03、`INSTR-02`。

方案：A. 不可覆盖的 Runtime/工具/数据完整性规则最高；在用户可配置层中，当前明确用户指令高于 `ContextPrompt`，`ContextPrompt` 高于全局 `SystemPrompt`；B. `ContextPrompt` 可以压过当前用户；C. 所有文本无层级拼接。

推荐 A。这样既保留全局和会话级长期偏好，又不会让一条旧 Prompt 否定用户刚刚给出的明确要求；仓库文本、工具输出和模型历史仍只是输入数据，不能自行进入这条权威链。

#### AQ-002 全局 `SystemPrompt` 的替换边界

状态：已答方向，边界待决。依赖：B-03、AQ-001。

方案：A. 只补充内置规则；B. 可替换人格但不能替换运行/安全规则；C. 完全替换。

推荐 A；如果确需人格覆盖则退到 B。用户配置不能删除工具配对、权限和恢复不变量。

#### AQ-003 `ContextPrompt` 生命周期

状态：A 的数据层已由 D-032 归档；命令、事件和权威细节待决。依赖：B-03、`CTX-07`。

方案：A. 随当前 XML 持久化并在恢复时生效；B. 只在当前进程有效；C. 每个 turn 单独设置。

推荐 A，符合“每个 Context 有 ContextPrompt、用 `.prompt` 设置”的回复。

#### AQ-004 默认 Agent 人格

状态：待决。依赖：AQ-001、AQ-002。

方案：A. 固定简洁、直接、技术型人格；B. 完全由 `SystemPrompt` 决定；C. 提供多个人格预设。

推荐 A。它给 yaca 一个稳定基线，又不增加人格配置系统。

#### AQ-005 项目指令自动发现

状态：待决。依赖：B-03、`INSTR-01`。

方案：A. 不自动发现，用户让模型按需读取文档；B. 固定读取一个项目根指令文件；C. 支持目录层级指令。

推荐 A，最符合“需要时自己整理文档让模型阅读”和保持简单的方向。

#### AQ-006 普通仓库文本的信任等级

状态：待决。依赖：`SAFE-10`、AQ-005。

方案：A. README、源码、命令输出一律是不可信数据；B. 让模型自行判断是否为指令；C. 自动升级命令式文本。

推荐 A。这是防止 prompt injection 绕过权限的根边界。

#### AQ-007 可移植 XML 中的 Prompt 快照

状态：待决。依赖：`CTX-15`、AQ-002、AQ-003。

方案：A. 保存每 turn 实际有效 Prompt 全文；B. 只保存配置引用；C. 保存全文、来源和 digest，但排除秘密。

推荐 C，使历史行为可解释并支持换机器接盘。

#### AQ-008 旁问的 system prompt

状态：待决。依赖：B-09、AQ-001。

方案：A. 主 Prompt 加强制只读/无工具的旁问规则；B. 完全独立 Prompt；C. 直接复用主 Agent，不加限制。

推荐 A，既让旁问看到会话，又不会暗中改变主任务或调用工具。

### TUI、输入与页面模型

#### AQ-009 快捷键实现基线

状态：部分。依赖：B-09、B-17、`PLAT-11`。

#### AQ-102 同一响应同时含文本与 tool calls

状态：待决。依赖：AQ-034、AQ-091、`MODEL-05`。

#### AQ-103 tool call 被接受的 durable 点

推荐 B。理由：崩溃后可以区分“未开始”“可能已经执行”和“已有结果”。

#### AQ-104 审批等待的持久状态

推荐 B。理由：审计信息不丢失，同时不能把崩溃前未完成的人工决定当成授权。

#### AQ-105 一次响应中的多个工具有一个失败

状态：待决。依赖：AQ-035、AQ-102、AQ-103。

推荐 B。理由：通用回滚并不可实现；顺序停止能控制连锁伤害并保持事实完整。

#### AQ-106 未知或畸形模型响应的重试

状态：待决。依赖：AQ-099、AQ-197、`MODEL-10`。

推荐 B。理由：协议错误通常不会通过相同请求自行修复，无限重试只会重复计费。

#### AQ-108 Model 切换的生效点

### 工具、进程与安全细化

#### AQ-111 工具描述符是否版本化

#### AQ-113 目录列表的递归边界

推荐 B。理由：避免误扫整盘、循环链接和旧磁盘长时间无响应。

#### AQ-114 文本搜索的实现后端

状态：待决。依赖：AQ-033、AQ-045、`TOOL-10`。

方案：A. 强依赖外部 `rg`；B. 内置可移植搜索基线，可用时选择性调用外部加速器但保持同一结果契约；C. 交给 shell 的 `findstr`/`grep`。

推荐 B。理由：XP 和最小 Linux 不保证安装相同命令，核心 Agent 工具不能因此消失。

#### AQ-115 写文件工具的覆盖语义

状态：待决。依赖：AQ-034、AQ-038、`TOOL-02`、`TOOL-09`。

方案：A. 默认无条件覆盖；B. 区分 create 与 replace，replace 要求期望摘要/版本匹配，写入使用原子替换；C. 只允许追加。

推荐 B。理由：可以发现模型基于旧内容写回的竞态，也能避免半写文件。

#### AQ-116 patch 工具的格式

状态：待决。依赖：AQ-034、AQ-115。

方案：A. 统一 diff；B. 带明确文件边界和上下文校验的结构化 patch，失败时不部分应用；C. 任意脚本修改。

推荐 B。理由：跨平台换行和路径规则可由 Runtime 统一处理，原子失败也更容易恢复。

#### AQ-117 是否提供显式删除工具

状态：待决。依赖：AQ-033、AQ-038、AQ-115。

方案：A. 不提供，只能 shell 删除；B. 提供带目标类型检查、确认和 operation ID 的 delete；C. 删除不需要权限。

推荐 B。理由：显式工具比解析 shell 更易审计和审批；删除仍应属于高风险能力。

#### AQ-118 重命名的禁止覆盖规则

状态：待决。依赖：AQ-117、`PLAT-04`。

方案：A. 目标存在就覆盖；B. 默认 no-replace，跨设备时明确报告不能保证原子性，覆盖必须是单独确认动作；C. 自动生成新名称。

推荐 B。理由：不同 Windows/Linux API 的默认覆盖行为不一致，必须先统一安全语义。

#### AQ-119 shell 工具接受原始命令还是 argv

状态：待决。依赖：AQ-034、AQ-038、`PROC-01`。

方案：A. 模型只看到一个接受原始字符串的 shell 工具；Runtime 内部另有不暴露给模型的结构化 process argv 端口，用于 curl/helper；B. 暴露 argv 与 shell 两个模型工具；C. 模型只接受 argv，完全禁止管道和重定向。

推荐 A。它符合项目负责人“交给模型调用原始工具、保持简单”的方向，同时避免 yaca 自己启动 curl/helper 时经过 shell。原始 shell 是宽能力，安全边界由 AQ-224 和新增 capability 矩阵诚实说明，不能靠解析命令字符串伪造细粒度隔离。

#### AQ-120 shell 的工作目录

状态：待决。依赖：AQ-107、AQ-119、`PROC-02`。

方案：A. 继承 Runtime 当前进程且工具可永久 `cd`；B. 每次调用都有显式 cwd，默认使用 turn 快照的工作目录，结果不得暗中改变全局 cwd；C. 永远固定项目根。

推荐 B。理由：并发、恢复和日志都能准确解释相对路径，`cd` 不会泄漏到后续调用。

#### AQ-121 子进程环境变量继承

状态：待决。依赖：AQ-119、AQ-120、AQ-148。

推荐 B。理由：编译工具通常依赖 PATH 等环境，但凭据不能无意进入日志或 Context。

#### AQ-122 stdout 与 stderr 的保存方式

#### AQ-123 子进程输出编码

状态：待决。依赖：AQ-045、AQ-122、`PROC-07`。

方案：A. 一律假定 UTF-8；B. 保留原始字节并按平台/显式 encoding 解码为 UTF-8，记录替换或失败；C. 一律使用系统 ANSI code page。

状态：待决。依赖：AQ-122、AQ-123、AQ-125。

#### AQ-125 工具输出截断

状态：待决。依赖：AQ-028、AQ-112、AQ-122、AQ-195。

推荐 B。理由：头尾通常同时包含命令背景和最终错误，明确标记可防止模型把片段当完整结果。

#### AQ-127 进程树无法完全终止时的状态

#### AQ-129 Git 是否使用专用工具

方案：A. 所有 Git 操作走 shell；B. status/diff 等只读动作可有结构化包装，提交/推送仍走明确权限的 shell；C. 实现完整 Git 协议库。

推荐 B。理由：模型、恢复器、XML 和 UI 才能引用同一项副作用并正确配对结果。

#### AQ-139 `Streaming=force` 但协议不支持

推荐 B。理由：`force` 的价值就是让缺失能力显性失败，静默降级会与用户选择相反。

#### AQ-140 Model 内的 Retry 字段

方案：A. 重试次数、退避和可重试错误策略都绑定每个 Model，同时 Runtime 保留任何配置都不能突破的内部安全硬上限；B. 改为一个全局 retry；C. 每种错误自由无限重试。

推荐 A。用户已经明确“重试和 Model 绑定”；待确认的是字段粒度、默认常量以及收到任何响应后是否一律禁止整请求自动重放。

#### AQ-141 请求超时字段的语义

推荐 B。理由：流式请求可能持续很久，连接失败与模型正常生成慢需要不同诊断。

### Context XML、索引、恢复与压缩细化

#### AQ-161 XML schema 是否公开且版本化

状态：部分。依赖：AQ-041、AQ-042、AQ-185、AQ-186。

方案：A. 将活动 `context.xml` 的元素、类型、顺序、兼容规则和示例作为公开读取契约；首版只有 yaca 是受支持 writer；B. 公开读取并同时承诺任意第三方可原地改写活动文件；C. 活动格式私有，另导出公开格式。

推荐 A。最直接兑现“复制 XML 后其他 Agent 可接盘”，又不把跨进程锁、提交 footer 和未知扩展的写入责任无条件交给第三方；以后可以单独发布 writer conformance contract。

#### AQ-162 XML 使用层级快照还是扁平事件日志

状态：待决。依赖：AQ-091、AQ-161、AQ-171。

方案：A. 只保存当前对话树快照；B. 单 XML 内使用逻辑上 append-oriented 的事件序列，加可重建的当前状态/摘要区；C. 每个 turn 独立 XML。

推荐 B。这里的“追加”只描述事件语义，不承诺在已经闭合的 XML 根元素后物理原地追加；实际发布仍按 AQ-172 的整文件或等价可恢复协议。事件能保留修改和中断历史，快照区又让第三方不必重放所有细节才能阅读。

#### AQ-163 Prompt 的 XML 表达

状态：待决。依赖：AQ-059、AQ-060、AQ-161。

方案：A. 只存当前 `ContextPrompt`；B. 当前值作为会话元数据，同时每次变更为事件，turn 记录有效 Prompt digest/版本引用；C. 每条消息重复完整 Prompt。

推荐 B。理由：可解释历史且避免大量重复，公开 reader 仍能直接找到当前值。

#### AQ-164 Model 切换的 XML 快照

状态：待决。依赖：AQ-065、AQ-108、AQ-159。

方案：A. 只存 Model 名；B. 切换事件保存逻辑名、协议、endpoint、远端 Model ID、窗口、Streaming/工具能力等有效非秘密投影及其 digest，每个 turn 引用有效版本；C. 保存完整 INI section 和 Key。

推荐 B。它能区分“同名但连接或能力已经变化”的配置，让目标机映射等价 Model；digest 只覆盖非秘密投影，绝不把 Key 变成可比对的凭据指纹。

#### AQ-165 工具输出怎样保持可移植

状态：待决。依赖：AQ-124、AQ-125、AQ-161。

方案：A. 所有原始输出无限内嵌；B. 内嵌有界规范文本/摘要、编码、截断信息和 digest；依赖工作区外部文件时明确标成不可移植引用，并把“证据不自包含”列入接盘检查；C. 只保留“成功”。

推荐 B。理由：单 XML 有尺寸边界，同时接盘者能区分完整证据、摘要和缺失附件；这支持 AQ-041 的“语义上可继续”，不等于所有原始证据都自包含。

#### AQ-166 审批记录的 XML 字段

状态：待决。依赖：AQ-039、AQ-104、AQ-161。

方案：A. 只存 allowed/denied；B. 存 operation ID、能力、目标摘要、请求理由、决定、范围、时间和决定来源；C. 把自然语言提示整段保存即可。

推荐 B。理由：能审计一次授权究竟覆盖什么，也避免把 session 授权误解释成永久权限。

#### AQ-167 未完成 assistant 消息怎样编码

状态：待决。依赖：AQ-030、AQ-091、AQ-162。

方案：A. 当作完整 assistant 消息；B. 明确状态为 streaming/interrupted/failed，保存已提交文本片段和 finish/error 原因，绝不注入为正常完成；C. 崩溃时删除。

推荐 B。理由：保留用户已看到的事实，同时恢复器不会误信一个被截断的结论。

#### AQ-168 配置快照的秘密排除

状态：待决。依赖：AQ-040、AQ-159、AQ-164。

方案：A. 复制所有有效配置；B. schema 标注 secret 字段，XML 只保存逻辑引用、非秘密投影及该投影的 digest；C. 仅凭字段名包含 `key` 来过滤。

推荐 B。理由：由 schema 驱动才能覆盖代理密码等非 Key 秘密，且不会因重命名字段漏掉；digest 本身也不得覆盖 Key 或其他秘密，避免形成可离线比对的凭据指纹。

#### AQ-169 工作区状态保存到什么程度

状态：待决。依赖：AQ-041、AQ-120、AQ-161。

方案：A. 打包整个工作区进 XML；B. 保存规范化逻辑工作目录、项目根、可选 Git HEAD/dirty 摘要和关键文件 digest；C. 完全不保存工作区信息。

推荐 B。理由：足以发现目标机代码状态不同，又不会把任意仓库内容塞入会话文件。

#### AQ-170 目标机器目录不一致时怎样接盘

状态：待决。依赖：AQ-041、AQ-159、AQ-169。

方案：A. 必须存在原绝对路径；B. 保留原逻辑路径用于解释，导入时让用户映射到新项目根并记录 mapping 事件；C. 自动按目录名在整盘搜索并选择首项。

推荐 B。理由：跨 Windows/Linux 或不同用户目录时路径必然变化，显式映射比全盘猜测安全。

#### AQ-171 事件完整性：序号还是 digest 链

状态：待决。依赖：AQ-162、AQ-189。

方案：A. 只有递增局部序号；B. 序号加每个事件内容 digest/前序 digest，可检测意外损坏但不宣称防恶意篡改；C. 公钥签名每个事件。

推荐 B。理由：实现成本适中，能定位截断和乱序；没有安全密钥体系时不应虚称真实性认证。

#### AQ-172 XML 提交方式

状态：待决。依赖：AQ-043、AQ-132、AQ-162。

方案：A. 原文件就地改写；B. 在同目录写完整临时 XML、校验并执行目标平台与文件系统实测证明的原子替换，或采用具有同等恢复证据的发布协议；C. 每个事件永久单独文件。

推荐 B。理由：在允许的辅助文件边界内最大限度避免半个正式 XML；`flush`、目录元数据同步和替换在不同 Windows/Linux 文件系统上的保证不同，必须分别证明，不能把一次 API 成功直接写成“掉电必然持久”。

#### AQ-173 临时文件命名和扫描忽略

状态：待决。依赖：Q-015、AQ-043、AQ-172。

方案：A. 任意 `.xml` 后缀；B. 使用不会被候选扫描器识别为活动 Context 的固定 ASCII 临时后缀/标志，并在启动时安全清理；C. 放到系统临时目录。

推荐 B。理由：同目录原子替换更可靠，同时通用名称/hash 搜索不会把未提交文件当成会话。

#### AQ-174 多进程写锁

状态：待决。依赖：AQ-043、AQ-103、AQ-172。

方案：A. 不加锁，最后写入者获胜；B. 每个 Context 只有一个 writer，使用平台窄适配器锁；只读浏览可并发，陈旧锁不能仅按时间盲删；C. 所有访问全局串行。

推荐 B。理由：避免两个 yaca 进程互相覆盖，也不阻塞安全的只读搜索。

#### AQ-175 损坏 XML 的修复策略

状态：待决。依赖：AQ-012、AQ-161、AQ-171、AQ-172。

方案：A. 静默丢弃坏尾并覆盖原文件；B. 隔离为只读诊断，把可解析残存内容标成未证实的 salvage preview，只有旧发布版本/备份/提交证据能够证明边界时才称为“已提交”，用户确认后另写新文件；C. 一律删除。

推荐 B。理由：单个损坏 XML 的可解析前缀不自动等于最后一次完整提交；恢复不能制造未经确认的新历史，原始证据必须保留供人工或新版本处理。

#### AQ-176 schema 迁移

状态：待决。依赖：AQ-161、AQ-175、AQ-185。

方案：A. 打开旧版时原地自动升级；B. reader 向后读取，确需迁移时先验证、生成新文件并保留来源版本和迁移报告；C. 旧文件拒绝打开。

推荐 B。理由：公开稳定格式仍会演进，非破坏式迁移让失败可回退且第三方可理解变化。

#### AQ-177 Unicode Context 文件名

状态：部分。依赖：Q-014、Q-015、AQ-045、`PLAT-09`。

方案：A. 名称强制 ASCII；B. 用户可用 Unicode/中文名，内部 XML 为 UTF-8，平台适配器负责原生路径编码和非法字符校验；C. 用 URL 编码显示。

推荐 B。理由：已确认示例本身包含中文；ASCII 约束只应用于机器字段和固定 UI 文案。

#### AQ-178 归档与删除的物理语义

状态：待决。依赖：AQ-083、AQ-117、AQ-174。

方案：A. 删除立即永久移除；B. archive 移到 `__yaca__/CONTEXT` 下明确的非活动区，delete 默认二次确认且说明是否可恢复；C. 只从索引隐藏但文件留在原位。

推荐 B。理由：浏览器需要区分“暂时不参与搜索”和“永久丢失”，且归档区不得进入通用连接搜索。

#### AQ-179 压缩摘要作为何种事件

状态：待决。依赖：AQ-061、AQ-099、AQ-162。

方案：A. 用摘要覆盖并删除原消息；B. 追加 compaction 事件，记录输入范围、模型/Prompt、摘要、未压缩控制状态和 digest，完整 canonical 历史始终保留；C. 只在内存中压缩且不留事实。

推荐 B。理由：压缩只能改变下一次送给模型的视图，不能删除 XML 中已经承诺保存的完整对话；接盘者也能知道哪些内容经过有损处理并验证摘要覆盖范围。

#### AQ-180 export/import 是复制还是可移植 profile

状态：待决。依赖：AQ-041、AQ-168、AQ-170。

方案：A. export 只是复制活动 XML；B. 区分原样 copy 与 portable export，后者做秘密检查、路径映射清单和兼容报告，仍不携带 Key；C. 导出完整 INI 和 XML。

推荐 B。理由：日常备份和跨机器迁移的风险不同，显式命令可以在迁移前暴露缺失依赖。

## P2：实现前需要冻结的精确常量与验证口径

推荐 B。理由：XML 是核心事实源；继续执行却不能记录会让恢复器既不知道发生过什么，也可能重复副作用。

推荐 B。理由：旧 shell 和测试可以可靠判断结果，又不会把上百个内部错误硬编码成永远不能调整的进程码。

#### AQ-249 Git 修改操作的产品边界

状态：待决。依赖：B-03、AQ-129、AQ-224、`TOOL-12`。

方案：A. yaca 自动 stash/commit/push；B. status/diff 可提供只读结构化视图，commit/reset/stash/push 等修改动作只在用户任务明确需要且 Permission 允许时由普通工具/shell执行，绝不因结束 turn 自动发生；C. 完全禁止模型运行 Git。

推荐 B。理由：它保留 Coding Agent 的实用能力，但不会把用户仓库历史当作 yaca 的隐式事务或发布动作。

#### AQ-250 原生 helper 的治理边界

状态：待决。依赖：AQ-223、AQ-206、AQ-207、`RUNTIME-02`。

方案：A. 原生层拥有配置、AgentLoop 和 XML 业务状态；B. 每个 helper 只有窄、版本化、可契约测试的能力 ABI，返回数据不持有领域状态；发行 manifest 固定架构/hash，安全的纯 Lua fallback 才允许降级；C. 动态加载系统任意同名 DLL。

推荐 B。理由：旧平台兼容确实需要少量原生能力，但业务留在 Lua 才能保持可测试、可移植和依赖可审计。

## 第三轮闭环审计追加问题：从主题覆盖到可实施契约

下面的问题来自对 `AQ-001` 至 `AQ-250` 的生命周期反向审阅。它们专门补“已有名词但没有信号来源、状态转换、安全边界或物理实现”的缺口。原子编号用于追踪；项目负责人实际按决策包成组回复，不需要逐条机械作答。

### AgentLoop 控制协议与本地身份

#### AQ-251 主模型怎样结构化表达任务结局

状态：待决。依赖：D-020、AQ-110、`LOOP-03`、`LOOP-25`。

方案：A. 版本化无副作用 control/tool，明确 `finish(completed|partial)`、`ask-user`、`refuse`；B. Runtime 解析自然语言判断；C. 任意无工具回复都算 completed。

推荐 A。只有明确的 typed control 才能可靠区分完成、等待用户、部分完成和拒绝；它不授予工具权限，DoubleCheck 也只在明确 finish 后触发。

#### AQ-252 普通无工具回复代表什么

状态：待决。依赖：AQ-251、`LOOP-03`。

方案：A. 只表示这次模型采样/当前 turn 向用户 yield，不自动宣告任务完成；B. 一律完成整个任务；C. Runtime 根据语气猜测。

推荐 A。模型可以自然地提问或报告进展；只有 AQ-251 的明确 control 改变任务终态。

#### AQ-253 provider refusal 与 content filter 怎样映射

状态：待决。依赖：AQ-101、AQ-251、`MODEL-09`。

方案：A. 规范化为独立 response outcome，保存可见说明，再由主状态机产生 `refused` 或 `partial`；B. 当网络错误自动重试；C. 当普通 completed。

推荐 A。拒绝不是传输故障，也不能伪装成功；若响应此前已有可用内容则可以是 partial，否则是 refused/waiting-user 路径。

#### AQ-254 流式 tool call 何时可执行

状态：待决。依赖：AQ-099、AQ-112、AQ-228、`MODEL-08`。

方案：A. provider response 合法结束、全部调用参数/数量/schema 验证且 canonical assistant response durable 后才接受；B. JSON 看似闭合就立即执行；C. 每个参数 delta 都尝试执行。

推荐 A。断流前看似完整的调用仍可能被后续修正；先执行会让失败响应产生不可逆副作用。

#### AQ-255 steer 到达时尚未执行的旧工具调用

状态：待决。依赖：AQ-087、AQ-234、AQ-254。

方案：A. 旧 response 中所有未开始调用形成 synthetic `skipped-by-steer` result，再把 steer 注入下一主请求；B. 先执行旧调用；C. 丢弃调用但不补 result。

推荐 A。插队纠偏必须能阻止尚未发生的动作，同时保持 tool-call/result 配对和完整审计；已开始的动作只能请求取消并保存真实结果。

#### AQ-256 一个 response 中多个 tool call 的串行结果

状态：待决。依赖：AQ-100、AQ-254、`TOOL-06`。

方案：A. 按规范顺序串行；某个失败/取消后，其余未开始调用都生成带原因的 synthetic skipped result；B. 首个失败后直接遗失其余调用；C. 全部并行。

推荐 A。它符合首版串行基线，也保证每个已接受调用都有确定结果，不让模型下一轮看到断裂历史。

#### AQ-257 XML 内部身份命名空间

状态：待决。依赖：AQ-091、AQ-171、AQ-190。

方案：A. 使用单 XML 内单调 ASCII 十进制身份，turn/request/operation 等可引用创建它的 event sequence；B. 所有对象用全局 UUID；C. 只依赖数组位置和 provider ID。

推荐 A。没有永久 ContextId 不等于没有局部关系身份；单调本地 ID 简单、可恢复且不随文件重命名改变。

#### AQ-258 provider ID 与本地 ID 的关系

状态：待决。依赖：AQ-221、AQ-257、`MODEL-08`。

方案：A. 本地 `tool_call_id/request_id` 永远由 yaca 分配，provider 原始 ID 作为可重复/缺失的证据字段保存；B. provider ID 直接成为本地身份；C. 丢弃 provider ID。

推荐 A。兼容端点可能缺失或重复 ID，本地关系不能因此碰撞；保留原值仍便于协议诊断。

#### AQ-259 模型请求 purpose 的正式集合

状态：待决。依赖：AQ-008、AQ-019、AQ-241、AQ-251。

方案：A. 固定 `main|side|action-review|termination-review|compaction|self-test` 六个核心 purpose，每类有独立 prompt/tool/budget 契约；若且仅若 PJ-12 B 被选中，再增加一次性条件 `context-name` 契约，但不把它伪装成常驻第七类；B. 全部叫 chat；C. 让 Model 名推断用途。

推荐 A。旁问、复核和压缩的权限与污染规则不同；purpose 是 Runtime 强制行为，不只是 Prompt 中的一句提醒。

#### AQ-260 每次请求保存实际 model view manifest

状态：待决。依赖：AQ-057、AQ-163、AQ-179、AQ-259。

方案：A. 请求记录所用消息范围、摘要、Prompt/Model/tool-schema snapshot 与切换事件引用；B. 只保存最后聊天文本；C. 保存完整 HTTP body 含 Key。

推荐 A。接盘者才能解释“模型当时真正看见了什么”，同时不把 secret header 和无限 wire trace 放进 XML。

### 旧平台事件泵、输入与文件系统

#### AQ-261 统一异步端口的总体拓扑

状态：待决。依赖：AQ-025、AQ-223、AQ-250、`RUNTIME-02`。

方案：A. 单线程 Lua 领域核心 + 平台异步/极小原生等待层，把 console、pipe、process、network 事件送入同一有界泵；B. 每个子系统各自阻塞；C. 多个线程直接共享 Agent tables。

推荐 A。它保留简单的单一状态所有者，又能真实支持流式输出、忙时输入和取消；需要原型证明而不是只靠 Lua coroutine 名称。

#### AQ-262 原生 I/O port 的最小 ABI

状态：待决。依赖：AQ-250、AQ-261。

方案：A. 版本化 `start/poll/cancel/join/close` 与有界 event schema，原生层不持有 Agent 状态；B. 让 C 层直接驱动会话；C. 为每个调用临时发明返回格式。

推荐 A。统一生命周期才能测试取消竞态、资源释放和 helper 崩溃；Lua 仍是业务真相源。

#### AQ-263 取消请求与真实完成竞态

状态：待决。依赖：AQ-027、AQ-127、AQ-262。

方案：A. cancel 只是请求，最终必须等待 completed/cancelled/failed/unknown 事件后收口；B. 发出 cancel 即声称未执行；C. 立即复用缓冲区和 operation ID。

推荐 A。Windows API 也不保证取消一定抢赢完成；领域记录必须反映最终可观察事实。

#### AQ-264 流式输出到达时如何保护正在编辑的 draft

状态：待决。依赖：AQ-067、AQ-239、AQ-261、`TUI-22`。

方案：A. raw editor 保存并重绘 draft；无法获知未提交字符的 cooked 后备暂存异步 UI delta，提交后再显示；B. 任意输出穿过输入行；C. 忙时完全不接受输入。

推荐 A。一个语义 TUI可以有能力降级；不能为了“流式”破坏用户已经输入但尚未提交的文字。

#### AQ-265 cooked-line 后备的即时状态

状态：待决。依赖：AQ-264、AQ-232。

方案：A. 周期状态合并并延后到安全换行，Esc/组合键由 `.cancel/.steer/.ask` 文本命令补齐；B. 仍承诺逐 token 与全部组合键；C. 拒绝在 cooked 终端运行。

推荐 A。核心动作完整，视觉即时性可保守降级；帮助页必须明确当前可用输入能力。

#### AQ-266 模型 raw shell 的固定方言

状态：待决。依赖：AQ-119、AQ-120、`PROC-01`。

方案：A. Windows 固定 `cmd.exe /d /s /c` 等经验证契约，Linux 固定 `/bin/sh -c`；B. Windows 默认 PowerShell、Linux 默认 bash；C. 继承用户任意默认 shell。

推荐 A。XP 不保证 PowerShell，CentOS 也不应假设 bash 语义；固定方言才能让模型 Prompt、转义和测试一致。

#### AQ-267 内部模块、DLL 与随包工具的搜索路径

状态：待决。依赖：AQ-212、AQ-250、`RUNTIME-04`、`THREAT-03`。

方案：A. 内部 Lua/C 模块和工具只按发行 manifest 的绝对路径加载，CWD、环境 Lua path/cpath 和系统 PATH 不参与；B. 优先当前工作区；C. 任意同名 DLL 都可加载。

推荐 A。工作区本来就包含不可信文件；用户 raw shell 的 PATH 语义与 yaca 内部依赖搜索必须分开。

#### AQ-268 直接文件工具支持哪些文件类型

状态：待决。依赖：AQ-113 至 AQ-118、`TOOL-10`。

方案：A. v0.1 默认只处理普通文件和真实目录，device/FIFO/socket 等拒绝；B. 对所有特殊文件按普通文件操作；C. 跟随任何对象且不报告类型。

推荐 A。旧系统和跨平台特殊对象语义差异太大；raw shell 仍可在宽 Execute 授权下处理高级场景。

#### AQ-269 symlink、junction、hardlink 与 TOCTOU 复核

状态：待决。依赖：AQ-213、AQ-225、AQ-268、`SAFE-13`。

方案：A. 审批展示规范/物理目标，执行时基于已打开对象身份重新复核；链接逃出工作区按外部目标，审批后替换则失效；B. 只检查文本路径一次；C. 一律跟随且不显示。

推荐 A。路径可能在模型读取、用户审批和执行之间改变；一次字符串前缀检查不能形成安全边界。

#### AQ-270 时间戳与 deadline 使用什么时钟

状态：待决。依赖：AQ-092、AQ-196、`PLAT-07`。

方案：A. 持久化 UTC wall-clock 与可选时区证据，超时/耗时用 monotonic clock；不可用时显式降级；B. 所有逻辑只用本地字符串时间；C. 用 CPU time 计算网络 deadline。

推荐 A。墙钟会跳变而单调钟不能跨重启；二者职责必须分开才能正确恢复和测试。

### 安全、权限、导入信任与秘密生命周期

#### AQ-271 raw shell 的宽能力名称和承诺

状态：待决。依赖：AQ-038、AQ-149、AQ-224。

方案：A. 命名为宽 `Execute/Shell`，明确允许后命令可能读取、写入、删除、联网、访问工作区外和启动子程序；B. 声称仍受 Read/Write/Network 逐项隔离；C. Runtime 正则解析命令后保证分类。

推荐 A。没有 OS sandbox 时 B/C 都无法兑现；Readonly 必须 deny Shell，Std 默认 confirm，最信任 profile 才可 allow。

#### AQ-272 Model 网络与工具网络的授权域

状态：待决。依赖：AQ-145、AQ-149、AQ-271、`SAFE-08`。

方案：A. 选择 Model 即授权对应 provider 请求；Permission.Network 只约束未来 direct network tool，raw shell 仍由 Shell 宽能力管；B. Readonly 禁止连接模型；C. 一个 Network 开关声称能阻止 shell 联网。

推荐 A。否则只读 Agent 连模型都不能工作，或给用户造成不存在的 shell 网络隔离错觉；若首版没有 direct network tool，可以不暴露 Network 字段。

#### AQ-273 tool × capability × profile 权威矩阵

状态：待决。依赖：AQ-033、AQ-149、AQ-150、AQ-271。

方案：A. 发布一张确定矩阵，列 direct read/write/delete/rename、raw shell、Model HTTP 和未来 direct network 的消费者与 deny/confirm/allow；B. 每次让模型解释需要什么权限；C. 只有 profile 自然语言描述。

推荐 A。配置项只有存在实际 enforcement consumer 才有意义，矩阵也是审批和测试的共同来源。

#### AQ-274 导入/外部放入 XML 的安全覆盖

状态：待决。依赖：AQ-159、AQ-180、AQ-237、`THREAT-05`。

方案：A. 忠实保存历史值，但继续运行前用本机 schema/profile 重算；降低本机安全默认的 Permission/DoubleCheck/Prompt 来源显著展示并确认；B. 外来 XML 静默获得所有历史权限；C. 删除全部会话参数。

推荐 A。可移植历史不等于可移植授权；既保留接盘信息，又阻止恶意 XML 关闭本机保护。

#### AQ-275 历史 approval 在恢复/导入后的效力

状态：待决。依赖：AQ-166、AQ-225、AQ-274。

方案：A. 永远只作 audit 事实，未执行动作在新进程/新环境重新判定和审批；B. 旧 allow-turn 永久有效；C. 导入者自动继承原机器身份。

推荐 A。动作、文件和配置都可能改变，历史批准不能成为重放令牌。

#### AQ-276 数据分类矩阵

状态：待决。依赖：AQ-040、AQ-168、`PROD-08`、`SAFE-09`。

方案：A. 按 Key/Prompt/用户正文/文件/命令输出/审批/诊断等分类，逐列规定可发给 main/reviewer/compactor、可显示/持久化/日志/导出；B. 全部同等公开；C. 只给一条“注意隐私”。

推荐 A。它是 Model、DoubleCheck、XML、日志与导出的共同上游，不能让各子系统各自猜秘密边界。

#### AQ-277 明文 Key 怎样交给 curl

状态：待决。依赖：AQ-040、AQ-136、`NET-03`、`SAFE-09`。

方案：A. curl config 走 stdin、request body 放权限受限临时文件；B. body 走 stdin、secret header 放权限受限临时 config；C. 使用窄 libcurl/native bridge，Key 只在进程内存。

推荐先以 A/B 做原型比较，再由“XP 文件权限、stdin 占用、崩溃残留和 curl 行为”证据选最简单可证方案；禁止 Key 进入 argv、环境、审批命令或普通 trace。C 只有在两种 subprocess 方案无法安全闭环时采用。

#### AQ-278 临时 secret/body 文件的生命周期

状态：待决。依赖：AQ-173、AQ-227、AQ-277。

方案：A. data-root 专用私有 temp、随机 no-replace 创建、最小权限、打开后写/flush、传递、关闭即删除；启动时按 manifest 回收残留并告警；B. 系统 temp 使用可预测名；C. 正文和 Key 永久留在命令文件。

推荐 A。清理失败仍应记录和可人工删除，不能因“最后会删”忽略崩溃窗口。

#### AQ-279 Permission、LLM 复核与人工审批顺序

状态：待决。依赖：AQ-019、AQ-020、AQ-104、AQ-225。

方案：A. 确定性 Permission → DoubleCheck action review → 人工确认 → durable operation → 执行；任一否决即不执行；B. reviewer 可授予 Runtime 拒绝的能力；C. 先执行再补审。

推荐 A。便宜且确定的限制先行，模型复核只能收紧，最终副作用前仍有可审计屏障。

#### AQ-280 reviewer 失败后能否人工 bypass

状态：待决。依赖：AQ-023、AQ-279。

方案：A. 允许用户对这一精确动作/完成意图显式 bypass once，并把失败、风险和 override 写入 XML；B. 永远无法继续；C. reviewer 失败自动通过。

推荐 A。DoubleCheck 是额外安全而不是单点永久锁死；override 必须精确且不能变成 session 全局关闭。

#### AQ-281 多个工具调用怎样复核和审批

状态：待决。依赖：AQ-100、AQ-256、AQ-279。

方案：A. 每个调用按顺序独立 verdict/approval，UI 可展示批次总览但授权绑定单项；B. 一次“全部允许”覆盖未知后续动作；C. 只复核第一个。

推荐 A。参数和风险可能不同；单项身份也能在中途 steer/cancel 后准确让剩余调用失效。

### Model 与完整配置语法

#### AQ-282 Model 的生成参数面

状态：待决。依赖：AQ-136、`MODEL-05`。

方案：A. v0.1 只提供跨协议有稳定语义的 `MaxOutputTokens`，Temperature/TopP/seed/reasoning effort 等走受限 protocol options 且缺失即不发送；B. 强制所有端点支持全套参数；C. 完全不可配置输出上限。

推荐 A。少字段不等于把 provider 特性硬编码；任何高级项都需明确类型、默认“不发送”和协议支持检查，不能用虚假通用默认改变模型行为。

#### AQ-283 费用预算与价格来源

状态：待决。依赖：AQ-028、AQ-153、AQ-282。

方案：A. v0.1 硬限制 request/token/time；费用仅在 provider 返回或用户配置版本化价格快照时估算显示；B. 无价格仍承诺精确 hard cost；C. 不显示任何使用量。

推荐 A。币种、缓存 token 和价格变更都会让隐式费率失真；先保证可实施的硬边界。

#### AQ-284 Endpoint 与 AuthMode 的精确语义

状态：待决。依赖：AQ-136、AQ-218、AQ-219。

方案：A. Endpoint 是完整请求 URL，Protocol 决定默认 auth header，受限 AuthMode/额外 header 只能显式配置且禁止覆盖 Runtime 必需字段；B. 任意拼接路径和 header；C. 仅支持厂商固定域名。

推荐 A。完整 URL 对自定义兼容端点最少猜测；Key 放 URL userinfo/query 必须硬错误。

#### AQ-285 Model 能力信息的权威顺序

状态：待决。依赖：AQ-081、AQ-142、AQ-144、AQ-202。

方案：A. 用户配置是授权事实，内置 preset 只预填，self-test observation 只告警不静默改写；B. 在线探测自动覆盖 INI；C. Model 名决定全部能力。

推荐 A。诊断证据可以发现不一致，但不能在用户不知情时改变工具、窗口或费用行为。

#### AQ-286 enabled 与 disabled Model 的完整性

状态：待决。依赖：AQ-080、AQ-136、AQ-160。

方案：A. disabled section 仍需语法/类型合法但连接字段可空；enabled 必须形成完整连接并通过静态校验；B. disabled 可含任意垃圾；C. 所有 Model 都必须在线可达才允许启动。

推荐 A。可以保存未完成草稿又不让 parser/writer 承担任意未知状态；离线不等于静态无效。

#### AQ-287 INI 多行 SystemPrompt/Context 文本语法

方案：A. 定义一种可转义、可精确往返的明确多行块语法和换行规范；B. 靠缩进/注释猜测；C. 禁止 Prompt 换行。

推荐 A。必须同时规定结束标记本身怎样转义、空字符串与缺失的区别、UTF-8 和最大长度，并提供 golden fixtures。

#### AQ-288 INI 注释、顺序和未知字段往返

状态：待决。依赖：AQ-037、AQ-133、AQ-152、`FMT-04`。

方案：A. parser 保留 section/字段顺序与可定位注释；保存已知字段时安全保留未知非安全字段，未知安全字段硬错误；B. REPL 每次重写并删除全部注释；C. 禁止手工编辑。

推荐 A。顺序决定默认 Model/Permission，仓库又把 INI 作为可读配置；若无法保留，必须先公开改变这一体验承诺。

#### AQ-289 无有效主配置时 model-repl 怎样启动

状态：待决。依赖：B-02、AQ-012、AQ-217。

方案：A. 正常 Agent 严格加载失败，但 `model-repl/config-repl/self-test --static` 使用受限 bootstrap reader，只允许诊断和事务式修复；B. 配置坏了所有命令都不能运行；C. 正常 Agent 忽略错误继续。

推荐 A。它不是首次运行向导，却能兑现项目负责人要求的手动首次配置与配置损坏可诊断路径。

#### AQ-290 手工编辑与 REPL 的跨进程冲突

状态：待决。依赖：AQ-133、AQ-288、`CFG-20`。

方案：A. 打开草稿时记录 digest/版本，保存前复核；外部变化则 compare/reload/discard，绝不盲覆盖；B. 最后保存者静默赢；C. REPL 长期独占整个配置文件。

推荐 A。用户可以手改 INI，事务式编辑必须保护这些变更；短 commit lock 不跨整个交互期持有。

#### AQ-291 “完整配置”的缺失与默认语义

状态：待决。依赖：AQ-131、AQ-185、AQ-286。

方案：A. typed schema 为唯一来源，生成模板写出全部常用字段；reader 可按兼容版本补安全默认，但每个 enabled Model/Permission 的必填字段必须存在；B. 每次升级要求用户手加所有新字段；C. 缺失值随实现代码路径变化。

推荐 A。“功能完整”是所有行为有 schema，不是逼用户显式重复每个内置默认；effective value 必须能在 REPL 查看来源。

### Prompt 人格与逐状态终端体验

#### AQ-292 Agent 默认回复语言

状态：待决。依赖：AQ-004、AQ-049、`PROD-15`。

方案：A. 程序标签/字段/error ID 固定英文 ASCII，Agent 默认跟随用户当前语言，SystemPrompt/ContextPrompt 可覆盖；B. Agent 永远英语；C. UI 标签跟随模型自由变化。

推荐 A。它符合“只做英文 UI”又不会强迫中文用户得到英语任务回答；机器协议仍稳定。

#### AQ-293 进度提示的触发与频率

状态：待决。依赖：AQ-005、AQ-069、`TUI-19`。

方案：A. 只在阶段变化、长等待超过阈值、重试/审批/阻塞时发简短 status，合并高频 token/tool delta；B. 每个内部步骤播报；C. 全程沉默直到结束。

推荐 A。旧终端不刷屏，用户也不会在慢网络/工具时误以为卡死；具体阈值后续用实测冻结。

#### AQ-294 最终报告的默认形态

状态：待决。依赖：AQ-007、AQ-110、AQ-251。

方案：A. 按任务规模自适应，但固定语义顺序：结果、验证证据、未完成/风险、必要下一步；简单任务可一句；B. 总是长模板；C. 只输出“done”。

推荐 A。兼顾简练和可验证，typed outcome 由 control 决定，正文不靠固定关键词供 Runtime 解析。

#### AQ-295 内置 Prompt 升级后恢复旧 Context

状态：待决。依赖：AQ-058、AQ-060、AQ-163。

方案：A. 历史 turn 保留旧 prompt snapshot；新 turn 使用新版内置 Prompt，并写明确 version-transition event；B. 假装历史由新版生成；C. 永远锁死旧 Prompt。

推荐 A。既能获得修复和新能力，又不会改写历史解释；重大不兼容升级可转只读/迁移门。

#### AQ-296 用户明确要求采用的项目规则文件

状态：待决。依赖：AQ-003、AQ-052、AQ-053、`INSTR-03`。

方案：A. 记录为用户委托的工作指导，优先于普通仓库内容但仍不能扩大权限或覆盖不可变安全规则；B. 始终当普通不可信文本；C. 自动把仓库任何规则提升为最高权威。

推荐 A。区分“仓库自称是指令”和“用户明确让我遵守该文件”，同时保留权限边界。

#### AQ-297 provider 不支持多层 role 时怎样扁平化 Prompt

状态：待决。依赖：AQ-001、AQ-054、AQ-218。

方案：A. 每个 Protocol 有版本化、确定性 delimiter/escaping 与 role flattening；仓库文本和工具输出永远作为引用数据区；B. 简单字符串拼接；C. 删除低层 Prompt。

推荐 A。否则同一 authority chain 在不同兼容端点会漂移，也容易被内容中的伪 delimiter 注入。

#### AQ-298 切换小窗口 Model 时 Prompt 已超限

状态：待决。依赖：AQ-062、AQ-235、AQ-240、AQ-297。

方案：A. 切换前计算不可压缩 Prompt/工具 schema；放不下则阻断并提示缩短 Prompt、换回足够 Model 或禁用工具；B. 静默截断最高权威 Prompt；C. 先发送等待 provider 报错。

推荐 A。系统规则与工具 schema不能靠尾截断，预检也能解释具体超限来源。

#### AQ-299 异步输出后的 draft 重绘视觉

状态：待决。依赖：AQ-264、`TUI-08`。

方案：A. enhanced input 在完整状态块后恢复提示符和 draft；plain/cooked 延迟状态到下一安全行并标记积压数量；B. 用光标任意覆盖 transcript；C. 清空用户 draft。

推荐 A。追加式 transcript 保持稳定，能力增强只改善编辑体验，不改变消息语义。

#### AQ-300 Markdown、代码和 diff 的渲染层级

状态：待决。依赖：AQ-070、AQ-071、AQ-192、`TUI-09`。

方案：A. plain 保留原文与 ASCII fence；basic 只增强标题/inline code/代码块/diff 行的颜色，不重排语义，不解析任意 HTML/ANSI；B. 全屏 Markdown 引擎；C. 所有内容去掉格式。

推荐 A。满足基本代码与 Git diff 可读性，又能在 XP/窄终端和复制输出时保持同一文本事实。

#### AQ-301 全部会话命令的状态可用性

状态：待决。依赖：AQ-031、AQ-098、AQ-234、`CLI-11`。

方案：A. 建立 command × AgentState 表，每格固定立即、下一 turn、排队、先取消或拒绝；context/delete/model/permission 等不能靠 handler 临时判断；B. 任意状态都直接执行；C. 忙时所有命令都当聊天。

推荐 A。尤其审批、执行工具、finalizing 和 recovery 状态必须避免切换上下文或使旧授权继续有效。

#### AQ-302 切换 Context 时 queue/steer/side 属于谁

状态：待决。依赖：AQ-088、AQ-234、AQ-301。

方案：A. 每项绑定创建它的 Context/turn；切换前收口 active turn，并让用户保留、删除或留在原 Context，绝不迁移到新 Context；B. 自动带到新 Context；C. 静默丢弃。

推荐 A。否则消息可能在错误工作区执行；未开始 queue 仍保存在原 XML 并可从恢复页管理。

#### AQ-303 单 XML 的物理提交路线

状态：待决。依赖：AQ-043、AQ-172、AQ-227、AQ-228。

方案：A. 每个 canonical durable 边界流式生成完整新 XML、验证/flush 后 replace，接受 O(n²) 累计 I/O 并设置硬门；B. 明确允许活动期间 durable WAL/recovery XML，安全点合并；C. 根未闭合或闭合后追加非法片段。

推荐先以 A 作为正确性基线并实测；C 直接排除。若最低机器超过已确认大小/延迟门，必须由负责人明确接受 B 或调整“活动事实始终单 XML”，实现不能暗中变更。

#### AQ-304 temp、lock、previous-valid 各是什么角色

状态：待决。依赖：AQ-043、AQ-173、AQ-174、AQ-303。

方案：A. 允许同目录瞬时 temp、稳定 writer lock/lease 和最多一个 previous-valid recovery generation；它们不参与 Resolver，角色写入恢复协议；B. 只有正式 XML，连锁都禁止；C. 任意 sidecar 都可长期成为第二事实源。

推荐 A。路径 replace 后锁旧 inode/handle 并不能自然保护新文件，稳定锁与最后有效代需要明确而有界的角色。

#### AQ-305 Context 大小/提交延迟达到硬门后怎样办

状态：待决。依赖：AQ-195、AQ-205、AQ-303、`PERF-02`。

方案：A. 提前告警并允许只读/导出/新建 Context；超过无法安全提交的硬门就 fail-stop，不再产生副作用；B. 无限增长直到内存/磁盘崩溃；C. 自动删除旧事实。

推荐 A。完整历史不能等同于无限资源；硬门必须由 XP x86/旧磁盘基准决定并在 UI 中解释。

#### AQ-306 公开 XML 是否支持第三方原地写入

状态：待决。依赖：AQ-042、AQ-161、AQ-237、AQ-304。

方案：A. v0.1 公开、版本化、第三方可读并提供 conformance reader；yaca 是唯一受支持 active writer；B. 任意程序写入都保证可继续；C. XML 只允许 yaca 自己读取。

推荐 A。跨 Agent 接盘首先需要语义可读，不等于第三方已经实现 writer lease、commit footer 和扩展往返；以后可单独开放 writer 规范。

#### AQ-307 Context 数量、归档与保留配额

状态：待决。依赖：AQ-178、AQ-244、AQ-305。

方案：A. 默认不自动删除；显示 Context 数量/总大小/最大单文件的软硬门，用户显式归档或永久清除；B. 最旧自动删除；C. 无任何配额或告警。

推荐 A。保持“完整历史”与用户控制，同时避免便携目录在旧磁盘上无限增长；回收区是否计入配额必须明确显示。

#### AQ-308 删除当前活动 Context 后的程序状态

状态：待决。依赖：AQ-098、AQ-178、AQ-301。

方案：A. 活动 writer 不能直接删除；先完整收口/释放锁，再选择归档并退出、切换其他 Context 或显式新建；B. 删除 XML 后继续写旧句柄；C. 自动创建同名空文件。

推荐 A。避免在用户以为已删除时又复活文件，也不把 queue/unknown operation 迁入新会话。

#### AQ-309 压缩摘要的稳定 schema

状态：待决。依赖：AQ-179、AQ-241、`COMP-03`、`COMP-07`。

方案：A. schema 校验的必填槽位：目标、用户决定、约束、文件/工作区变化、验证、失败尝试、未知副作用、待办、Model/Prompt 切换；B. 任意一段散文；C. 只保留最后 assistant 回复。

推荐 A。结构可跨模型测试和人工纠正；仍允许每个槽位内使用简洁自然语言。

#### AQ-310 压缩不能拆开的事件原子组

状态：待决。依赖：AQ-165、AQ-166、AQ-179、AQ-309。

方案：A. tool call/result、operation/approval/result、用户输入/直接回复、当前 active turn 与 unknown side effect 均作为不可拆组；B. 按单条 XML event 任意切；C. 只保留模型文本。

推荐 A。否则模型会看到没有结果的调用、没有动作的批准或丢失未确认副作用，压缩反而破坏可继续性。

#### AQ-311 切回更大窗口 Model 时是否恢复更多原文

状态：待决。依赖：AQ-164、AQ-240、AQ-309。

方案：A. 从完整事实历史重新构建更丰富 view，能放下时减少/跳过旧 summary，同时记录 view manifest；B. 永远只用压缩摘要；C. 删除旧摘要事件。

推荐 A。XML 保存完整历史的价值之一就是可在更大窗口恢复细节；旧摘要仍作为事实保留但不必成为当前 view。

#### AQ-312 v0.1 是否承诺自动 undo/preimage

状态：待决。依赖：AQ-115、AQ-165、AQ-249、`CHANGE-03` 至 `CHANGE-07`。

方案：A. 首版只保证 expected digest、单文件安全写、diff、operation/result 和不自动重放，不承诺通用自动 undo；B. 所有 direct write 保存完整 preimage 并可撤销；C. raw shell 也宣称可完全回滚。

推荐 A。B 会把大文件、二进制与秘密复制进单 XML或新增附件系统，C 无法兑现；若负责人选择 B，必须同时批准存储、配额、隐私和跨机迁移设计。

### 启动、恢复、self-test 与发布生命周期

#### AQ-313 新 Context 何时物理创建

状态：待决。依赖：AQ-060、AQ-215、AQ-216。

方案：A. 第一条用户输入成功 durable 时创建；只启动后退出不留空 XML；B. 每次裸启动立即创建；C. 第一次工具调用才创建。

推荐 A。避免空会话堆积，又保证接受输入前已有恢复事实；启动页可显示暂定名称但不先落盘。

#### AQ-314 多个启动错误同时存在时的优先级

状态：待决。依赖：AQ-012、AQ-215、AQ-217、`ARCH-02`。

方案：A. 固定平台/资源 → schema/配置 → 命令参数/目录 → Context 锁/恢复 → Model 可用性 → terminal 能力；一次报告所有可安全发现的同层错误；B. 按代码偶然顺序；C. 先联网再验证本地。

推荐 A。用户每次修复后不会被随机的下一错误打断，且启动仍不因诊断隐式联网。

#### AQ-315 如何判定 Context 未正常关闭

状态：待决。依赖：AQ-167、AQ-174、AQ-229。

方案：A. commit footer/turn 状态与 lease 证据共同判断，不能只看文件修改时间；B. 超过几分钟都算崩溃；C. 只看最后 assistant 文本。

推荐 A。系统休眠、时钟回拨和外部复制都会让时间启发失真；恢复原因必须可解释。

#### AQ-316 unknown operation 的人工解算

状态：待决。依赖：AQ-030、AQ-103、AQ-230。

方案：A. 用户可记录“确认已完成/确认未完成/仍未知”及证据，产生新 durable resolution event；不改写旧事实；B. 自动假定失败并重放；C. 从 XML 删除 operation。

推荐 A。外部世界无法总被程序探测，显式解算能让后续模型知道仍有哪些风险。

#### AQ-317 self-test 第二阶段单个 Model 失败后的流程

状态：待决。依赖：B-02、AQ-137、`DIAG-11`。

方案：A. 继续检查其余已启用 Model，逐项保存结果；第三阶段只使用明确通过的候选且先征得同意；B. 第一个失败立即停止所有；C. 自动禁用失败 Model。

推荐 A。一次网络故障不应掩盖其他配置问题，也不能让诊断静默改写权威 INI。

#### AQ-318 self-test 第三阶段的范围和发布地位

状态：待决。依赖：AQ-202、AQ-317。

方案：A. 选一个已通过的 Model 检查配置语义/命名合理性，结果只是带证据的 advisory warning，不是确定性发布硬门；B. LLM 评分决定配置能否启动；C. 调用所有 Model 无限互评。

推荐 A。诸如“名叫 Yolo 却只读”是有用建议但非机器真理；静态/协议测试才是 hard gate。

#### AQ-319 self-test 在线阶段的知情页

状态：待决。依赖：AQ-137、AQ-246、AQ-317。

方案：A. 开始前列 endpoint、Model 数、预计请求上限/可能费用、发送数据类别和代理/CA；用户可取消或只跑选中项；B. 静默联网；C. 把完整配置与 Key 发给 reviewer。

推荐 A。符合无隐式联网和明文 Key 边界，也让旧网络上的失败可预期。

#### AQ-320 self-test 的非 TTY 输出与退出类别

状态：待决。依赖：AQ-202、AQ-247、AQ-248。

方案：A. 静态阶段可非 TTY，固定 ASCII 行/可选机器格式与稳定 exit class；在线阶段必须显式 flag，不询问时 fail-closed；B. 管道中弹交互菜单；C. 所有 warning 都退出 0 且无法区分。

推荐 A。脚本可可靠使用基础诊断，又不会自动批准费用和外部请求。

### Provider wire、网络失败与 CLI 精确契约

#### AQ-321 网络重试按发送阶段怎样判定

状态：待决。依赖：AQ-140、AQ-197、AQ-221。

方案：A. 请求体未发送的 DNS/connect/TLS 可重试；可能已发送但无 response 记 outcome-unknown，除非协议有幂等保证；收到任何规范事件后禁止整请求重放；B. 所有 timeout 自动重试；C. 永不重试连接失败。

推荐 A。POST 可能已计费或生成结果，“没收到响应”不等于服务端没处理；request 与 attempt ID 分离。

#### AQ-322 HTTP 解压与资源炸弹

状态：待决。依赖：AQ-125、AQ-245、`NET-08`。

方案：A. 分别限制压缩体、解压后字节、ratio、header、单 SSE event、总响应和缓冲队列，超限取消并返回 typed limit error；B. 只看 Content-Length；C. 无界自动解压。

状态：待决。依赖：AQ-025、AQ-026、AQ-259、AQ-260。

方案：A. 最多一个 active side，使用创建时最近 durable model view snapshot、当前 Model 的独立 request/token/time 上限、无工具、独立 cancel；B. 无界并发；C. 与主请求共享可变消息数组。

推荐 A。能实现“直接回复”又保持 Win32 x86 内存、费用和历史污染可控；side result 作为 audit 事实不自动进入主 view。

#### AQ-360 实施前是否需要逐页面 golden transcript 与逐状态 golden trace

状态：待决。依赖：AQ-301、AQ-331、AQ-343、AQ-350。

方案：A. 每个主要页面/失败/恢复状态有 plain ASCII golden transcript，每个 AgentLoop 转换有 durable event trace；平台增强只能在不改语义下另测；B. 实现后凭截图决定；C. 只测函数返回值。

推荐 A。它把“页面风格”和“核心状态正确”一起变成可审阅证据，也是旧终端兼容最直接的回归保护。

## 第四轮交叉缝隙追加问题

下面十三项不是把旧题换个标题。它们来自对运行中外改、`ask-user` 后续、管理型删除、shell stdin、文件系统支持和隐私擦除等接缝的敌对式审阅。其余第四轮发现已经能扩展现有 AQ 或进入技术证明，不另造重复题号。

#### AQ-361 运行中外部修改配置的 reload 语义

状态：待决。依赖：`CFG-11`、`CFG-24`、`LOOP-15`、AQ-290。

场景：yaca 已在运行，用户用外部编辑器改变 `config.ini` 的 Key、Endpoint、Permission 或预算；文件保存过程中还可能短暂处于不完整状态。当前 turn 已冻结旧值，下一 turn 应使用哪一版不能交给文件 mtime 猜测。

方案：A. 外部改动永不自动载入，只在显式 reload 或重启后全量验证；yaca 自己的 model/config REPL 保存后可以在回到 chat 时明确提出从下一 turn 使用新版本；B. idle/turn 边界检测 digest 变化，展示脱敏差异并由用户确认载入，无效新文件保持旧内存值但阻止新 turn；C. 文件一变化就热应用能解析的字段。

推荐 A。它最简单，也不会让同一 turn 中途改变 endpoint 或权限；若日后实测重启/reload 太繁琐，再增加 B。C 会让临时半文件和安全字段漂移，不采用。

#### AQ-362 每个 Model 的并发、间隔与冷却

状态：待决。依赖：`MODEL-15`、`CONC-04`、`NET-06`、AQ-359。

场景：六个核心 purpose 可能同时或连续使用一个 Model；若 PJ-12 B 生效，每 Context 一次的 `context-name` 也经过同一 Model。本地端点可能只允许单并发，套餐端点也可能有请求间隔和 `Retry-After`。

方案：A. 不增加 Model 调度字段，只允许既有 main+side 并发，429 后临时按服务端提示等待；B. 每个 Model 至少有 `MaxConcurrentRequests` 与 `MinRequestIntervalMs`，所有 request purpose 共用调度器和 `Retry-After` 冷却，复杂 RPM/TPM token bucket 暂缓；C. 整个 yaca 同时只允许一个 Model request，不区分 Model，也没有 per-Model 字段。

推荐 B。两个简单字段能表达单并发本地模型和常见服务限制，又不会把首版配置变成计费平台。局部调度永远不能突破进程 hard cap；普通 Agent purpose 归入所属 Context/turn aggregate，显式 self-test 在没有 Context/turn 时使用独立 `self_test_run` aggregate；条件 `context-name` 只计 Context/runtime 与固定 lifecycle budget，不回记已结束 turn。

#### AQ-363 `ask-user` 回复属于哪个 turn

状态：待决。依赖：`LOOP-01`、`LOOP-28`、AQ-251、AL06-02。

场景：主模型用 typed `ask-user` 等待信息，用户数小时后回答。旧 turn 可能已经消耗预算，期间 Model、Permission、Prompt 或目录也可能改变。

方案：A. 回答继续使用原 turn ID、旧冻结配置和剩余预算；B. `ask-user` 把当前 turn 收口为 waiting-user，回答建立新 turn，以 `reply-to`/pending-question 引用保持任务因果，并重新冻结配置与预算；C. 回答只拼进下一次 HTTP body，不先成为 durable 用户事件。

推荐 B。任务语义仍连续，但用户输入、配置、生效点和账本都有清楚边界，也避免一条 turn 跨几天持有旧权限。

#### AQ-364 用户主动 retry 的可重放边界

状态：待决。依赖：`LOOP-29`、`NET-07`、`LOOP-14`、`TOOL-15`、AQ-316。

场景：错误卡显示模型 timeout、tool failed 或 shell outcome unknown。如果只有一个模糊的 `retry`，用户无法知道它会重试连接、重新生成，还是再执行一次副作用。

方案：A. `retry` 原样重放最后一步，不区分类型；B. 只有确认请求体未发送/尚无规范响应等安全阶段，Runtime 才能为同一 logical request 建新 attempt；无 accepted side effect 的 `regenerate response` 是同 turn 新 request，终态后的 `retry task` 是带因果链接的新 turn，accepted/unknown operation 只能 inspect/reconcile；C. 完全不提供手动入口，用户自己重新输入任务。

推荐 B。界面统一使用 `retry connection`、`regenerate response`、`retry task`、`inspect unknown` 四个准确动作，不使用没有对象的 `retry` 或同义 `send again`。

#### AQ-365 未提交 draft 是否属于完整 Context

状态：待决。依赖：`TUI-28`、`CTX-23`、AQ-264、AQ-351、AQ-353。

场景：用户写了多行内容但还没按发送，程序崩溃或窗口被关闭。持续保存可以找回草稿，却会把用户尚未提交的敏感文字写入 XML，并提高单 XML 重写频率。

方案：A. 只有已提交的 main/queue/steer/side 输入 durable；draft 只驻当前进程，崩溃可丢失，并明确显示 `not saved`；B. idle debounce 后把 draft 写成可删除的 XML session state；C. 建立独立 draft 文件。

推荐 A。这样“完整 Context”从明确提交动作开始，隐私与物理写入边界最简单；正常切页面时仍可在内存中保护 draft。

#### AQ-366 `.history` 与 `.details` 的恢复承诺

状态：待决。依赖：`TUI-29`、`CTX-01`、`CTX-06`、AQ-125、AQ-165。

场景：恢复昨日 Context 后，用户输入 `.details tool:21`。若详情只在旧 UI cache 中就无法查看；若宣称能看“完整原始输出”，又会和 canonical tool result 的有界截断冲突。

方案：A. 两个命令只查看当前进程缓存，退出即失效；B. 从 canonical XML 与稳定局部 event ID 派生；`.history` 是事实 transcript 的视图，不是另一份永久输入历史，`.details` 只展示 XML 真正保存的完整/截断/引用事实；C. 新增长期 history/detail 文件。

推荐 B。它让恢复和跨机接盘一致，又不会假装被资源上限丢弃的字节还能找回。

#### AQ-367 模型 raw `exec` 的 stdin

状态：待决。依赖：`PROC-11`、AQ-128、TS-09。

场景：命令意外显示 `Are you sure?`，或恶意子进程读取 yaca 的终端输入。若 raw exec 继承 stdin，它可能偷走聊天、queue 或审批按键；若做交互桥，则首版实际引入了 PTY/console 转发系统。

方案：A. 模型 `exec` 的 stdin 固定关闭/EOF，v0.1 只支持非交互前台命令；yaca 内部 curl/helper 各自显式声明受控 stdin source；B. 默认继承 yaca stdin；C. 正式支持交互 PTY/console 透传。

推荐 A。需要静态输入的命令可由 raw shell 自己使用管道/重定向表达；真正交互程序留待独立系统设计。

#### AQ-368 Context 内秘密的选择性擦除

状态：待决。依赖：`CTX-28`、`SAFE-09`、AQ-238、AQ-349。

场景：用户把 token 粘进普通消息或命令。它可能进入正式 XML、previous-valid、临时文件和导出，也可能已经发送到 provider。完整事实历史与“只删这一段”不能同时靠静默文本替换实现。

方案：A. v0.1 不支持原地 message redaction，只支持整 Context purge 与显式 sanitized export，并说明已发送内容无法撤回；B. 提供版本化 redaction rewrite，新 generation 删除选定正文并清理 yaca 知道的旧副本，但只承诺 best-effort，不声称物理 secure erase；C. 允许直接编辑 XML 且不留下结构化记录。

推荐 A 作为简单诚实的首版边界。如果保留任务同时删秘密是硬需求，再选择 B 并把 digest、backup、迁移和恢复整体重新设计；C 不采用。

#### AQ-369 管理型破坏动作的共同事务

状态：待决。依赖：`ARCH-05`、`CFG-10`、`CTX-11`、`INDEX-15`、AQ-080、AQ-178。

场景：config-repl reset、model-repl 删除仍被 Context 引用的 Model、context-repl 永久清除或 import/migrate 都不是模型 tool call，不能合法复用历史 Agent approval，却同样可能丢数据。

方案：A. 三个 REPL/CLI 各自设计 yes/no 和保存流程；B. 共用非 Agent 的 `ManagementMutation` 契约：plan、精确 target、影响/引用、stale check、默认 cancel、durable commit、typed result 和 recovery；C. 把这些动作伪装成 Agent tool 并继承旧 approval。

推荐 B。界面可以不同，但数据损坏防线和默认取消必须同源；它不增加新的 Permission profile。

#### AQ-370 Context 数据根与 workspace 的文件系统支持矩阵

状态：待决。依赖：`PLAT-13`、`PLAT-04`、`CTX-21`、`REL-02`、TP-011。

场景：Context 数据根可能在 FAT32/U 盘/SMB/NFS，workspace 可能在网络盘。前者需要可靠 lock、replace 和 durable commit，后者即使保证较弱仍可能是用户真实项目。

方案：A. 数据根和 workspace 都只允许完整证明过的本地文件系统；B. Context/config 数据根只允许通过 durability/lock 证明的文件系统，workspace 可以位于其他可访问文件系统，但 direct write/rename 根据能力 fail-closed 并显著说明降级；C. 对所有可写文件系统宣称相同原子、锁和掉电保证。

推荐 B。它把核心历史的强保证与项目目录的实际可用性分开；具体 NTFS/FAT/SMB/ext4/NFS 矩阵由目标平台证据填写。

#### AQ-371 raw shell 命令超过平台传输边界

状态：待决。依赖：`PROC-12`、AQ-119、AQ-266。

场景：模型生成的 raw 命令超过 CreateProcess/目标 shell 可安全传递的长度，或含无法按固定 shell 输入编码无损表示的字符。

方案：A. v0.1 返回 typed length/encoding error，让模型缩短或自己通过已授权文件工具创建脚本；B. Runtime 自动在受保护目录生成脚本并执行；C. Runtime 自动拆成多条命令。

推荐 A。B 需要另行定义脚本编码、权限、secret、删除、审计与语义等价；C 可能改变控制流和副作用，不能自动做。

#### AQ-372 活动工作目录中途失效

状态：待决。依赖：`PROD-16`、`CTX-13`、`LOOP-07`、AQ-269。

场景：active turn 中，工作目录被外部重命名、删除、网络断开或卸载；已经批准但尚未执行的工具仍保存旧 cwd/目标。

方案：A. 当前副作用 fail-stop，取消/收口在途动作；Context 保持可只读检查，显式 rebind 后生成新的 workspace/Prompt/Permission 快照；B. 沿用进程可能仍持有的目录句柄继续，路径显示以后再修；C. 自动猜测同名目录并重绑。

推荐 A。目录身份变化会让旧审批、相对路径和 Prompt 全部过期；不能靠名称猜测继续。

#### AQ-373 v0.1 扩展运行时的关闭边界

状态：A 已由 D-038 归档；当前只需规格化 unsupported、无空壳检查和未来显式 re-entry gate。依赖：`PROD-04`、`PROD-11`、`EXT-01` 至 `EXT-03`、`TOOL-14`、`LOOP-21`。

方案：A. v0.1 采用封闭核心，只运行随包内置工具和内部生命周期逻辑；MCP、自定义第三方工具、进程内插件、用户 hook、skill 包和子 Agent 全部排除运行支持，只保留来源 ID/schema version 等有真实消费者的窄语义接缝；B. 首版开放一个受限进程外工具协议，其余仍排除；C. 首版同时开放 MCP、Lua 插件、hook 和子 Agent。

推荐 A。完整 v0.1 指所选闭环质量完整，不是功能种类无限；排除后也不实现空 loader、公共 Lua API 或无消费者配置。
