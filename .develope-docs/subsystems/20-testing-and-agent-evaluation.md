# 20 测试、Agent 评估与平台验收

更新日期：2026-07-22

状态：**计划已确认（C01 + 每 task + C32）**；test tree、golden/fault/integration/qualification 边界已冻结，场景阈值由 manifest/target benchmark 校准

## 为什么需要独立子系统

16 号系统负责构建、装配和发布，15 号系统负责用户可运行的自检与诊断；它们都不能代替开发阶段的证据体系。yaca 还需要明确回答：哪些行为可以确定性证明、怎样复现崩溃边界、怎样评价非确定性的 Agent 行为，以及怎样证明发行包确实能在声明支持的旧系统上工作。

本文件主责 `TEST-01` 至 `TEST-10` 与 `EVAL-01` 至 `EVAL-08`，并承接 `REL-05` 至 `REL-09`、`REL-12`、`REL-13`、`DIAG-01`、`DIAG-02`、`LOOP-03`、`LOOP-09`、`LOOP-22` 等跨系统问题。这里记录候选测试架构，不预先决定具体测试平台和 CI 服务。

## 职责

- 建立从设计决策、系统不变量、测试场景到发布证据的可追踪关系。
- 为纯 Lua 逻辑、平台端口、模型协议、AgentLoop、上下文、权限、工具和 TUI 定义不同层次的测试方法。
- 提供可控的模型、网络、时钟、文件系统、进程、终端和随机数替身，使边界条件能够稳定重放。
- 定义故障注入点，验证取消、超时、断流、半写入、磁盘满和进程崩溃后的 durable 状态。
- 把 Agent 场景评估与传统通过/失败测试分开，记录成功证据、波动和回归阈值。
- 保存每个正式发行产物在真实目标平台上的验收结果，而不是只验证开发机源码。

## 边界

- 本系统不定义“完成”“安全”或“可恢复”的产品含义；这些分别由 AgentLoop、权限、上下文等主系统定义，本系统把它们变成可执行验收条件。
- 自检是交付给用户的诊断能力，测试夹具是开发证据；两者可以复用探测逻辑，但不能共享会泄露测试后门的运行路径。
- Agent 评估不能证明底层状态机正确，也不能用“模型大多数时候能处理”掩盖 tool call/result 不配对、越权或损坏历史。
- 本系统的“Agent 场景评估”是开发与发布证据；运行时由有效 `DoubleCheck` 触发的“完成复核请求”属于 05、06、09 号系统，本系统只测试总开关、独立请求身份和 verdict 控制流是否符合已确认契约。
- 模拟平台不能替代真实平台验收；真实平台验收也不能替代可快速定位失败的确定性测试。
- 发布门槛与撤回策略由 16 号系统执行，本系统只产生结构化结果与证据。

## 核心验收对象

一次 Agent 场景的判定不能只比较最终自然语言。候选证据至少包括：

- `turn_ended` 的 typed reason，以及是否与实际停止原因一致。
- durable 事件序列是否满足顺序、配对、唯一结束和恢复不变量。
- 工作区前后快照或 diff，以及既有用户改动是否保持不变。
- 实际执行、拒绝、取消和未执行的工具与副作用清单。
- 要求验证时的命令、退出状态、截断信息和结果摘要。
- 权限请求与授权范围是否匹配，禁止动作是否确实没有发生。
- 面向用户的完成、部分完成、阻塞或失败报告是否包含必要证据和下一步。

自然语言内容只适合检查必要事实、禁止事实、结构或人工评分，不宜默认做逐字 golden comparison。

## 候选四层证据结构

### 第一层：确定性核心测试

目标是快速证明同一输入必然得到同一结构化结果，主要覆盖：

- 纯 Lua 单元：解析、规范化、合并、预算、状态转换、错误分类和路径规则。
- 端口契约：文件、进程、网络、时钟、终端和持久化适配器对相同输入满足同一契约。
- AgentLoop trace：以脚本化模型事件和工具结果驱动状态机，比较 typed outcome 与 durable event trace。
- 完成复核路径：分别覆盖 `DoubleCheck` 关闭、复核允许、复核拒绝、无效 verdict、超时和请求失败，证明复核请求与主模型请求身份、用量和结果不会混淆。
- 格式与迁移：确定性编码、旧版本样本、损坏样本、未知字段和往返行为。
- 上下文路径与索引：对镜像路径、CJK 名称、固定 16 位动态 hash、无永久 ContextId、由近到远的搜索范围、实时派生、重命名、损坏/临时文件和路径边界使用固定夹具验证。
- 统一 Resolver：同一 selector 经 CLI、点命令和浏览器精确输入得到相同结构化结果；打乱目录枚举顺序不改变结果，非 hash 输入不计算 hash，每个 XML 候选在一次解析中最多探测和匹配一次，近层 hash 不被远层名称或 hash 推翻；当前环部分不可读时必须返回 `ScanIncomplete`，不得把已观察到的单个命中宣称为唯一或越过本环连接外层结果。
- 上下文浏览器：以控制器动作脚本验证目录导航、搜索、选择、刷新、重命名、删除确认和过期快照；原生快捷键路径与逐行文本后备对同一动作序列产生相同语义结果。
- TUI golden transcript：验证线性语义、无颜色标记、stdout/stderr 和控制字符清理，不绑定易变的耗时或 spinner 帧。

这层必须能在无网络、无真实模型、无系统级安装动作的环境运行。模型替身应播放规范化事件，而不伪装成某一家 provider 的完整服务。

### 第二层：故障注入与恢复测试

目标是在明确提交边界上制造失败，并证明系统不会谎报完成或留下不可解释状态。候选注入点包括：

- 用户输入已提交、模型请求尚未开始。
- 流式文本进行中、tool call 参数刚完整或响应已部分到达。
- 有副作用工具开始前、外部副作用完成后但结果尚未 durable。
- 权限请求已记录但尚未回答，或授权已记录但动作尚未开始。
- 事件记录写入一半、flush 失败、磁盘满、只读目录或尾部损坏。
- 压缩已生成但替换视图尚未提交，或连续压缩无收益。
- 模型、网络、工具、审批和压缩各状态收到取消。
- 进程异常退出后重新启动，并遇到遗留 running tool、retry 或 pending approval。
- 在上下文创建/rename 完成目标检查后由非协作进程抢先创建同名文件，证明 `publish_new_no_replace`/`move_no_replace` 返回冲突且绝不覆盖对方内容；普通 POSIX rename 行为不能作为测试替身蒙混通过。

故障计划应能固定随机种子、虚拟时钟和调度顺序。涉及真实进程崩溃或操作系统缓存的场景另设集成测试，不能只在内存替身中宣称已验证稳定存储。

### 第三层：Agent 场景评估

目标是衡量“Agent 能否完成有意义的任务”，而不是重新验证 Lua 分支覆盖率。建议分成三类：

1. **脚本化闭环**：固定模型事件，作为确定性发布门槛，验证读取、修改、验证、拒绝、取消和恢复的完整闭环。
2. **录制协议重放**：保存经过脱敏和版本化的 provider 事件样本，发现流式解析、工具参数和结束原因回归；录制物不自动成为真实模型能力评估。
3. **真实模型评估**：对版本固定的模型、prompt、配置和场景重复运行，统计完成率、安全违规、无进展、工具次数、token/时间和人工质量评分。

真实模型评估天然会波动。候选规则是：确定性的安全与状态不变量任何一次失败都阻断；任务质量使用重复样本、置信区间或明确阈值判断，不因单次措辞变化阻断。模型版本、endpoint 行为不可冻结时，结果必须标注为观测证据，而不是可复现构建证明。

### 第四层：真实平台与发行包验收

目标是验证用户收到的产物，而不是仓库中的源码。至少应覆盖：

- 从干净系统解压，无系统 Lua、无开发机 PATH 帮助时原地启动；再验证薄安装脚本的简单检查与 PATH 行为。
- 首次配置、离线启动、模型调用、工具闭环、取消、退出和恢复。
- 目标文件系统、路径、代码页/locale、80×24 终端、无 ANSI 和重定向输出。
- 随包 Lua runtime、launcher、curl/CA 与其他 native 文件的架构和最低系统 API。
- 只读目录、空间不足、长路径边界、进程树清理和旧 TLS 失败的用户诊断。
- 从其他 cwd 或经 PATH 启动时，`__yaca__` 仍与实际可执行文件相邻；手工替换 zip 后不出现内置更新器、安装数据库或隐式数据迁移行为。
- zip 根布局、SHA-256、component/license manifest、SBOM、构建摘要和完整测试摘要与 16 号系统一致。

Win32 x86 产物需要在 XP SP3、Vista SP2、7 SP1、8、8.1、10、11 上执行完整验收；Win64 x86_64 产物需要在 7 SP1、8、8.1、10、11 上执行完整验收。Linux x86_64 以 CentOS 7 为最低基线，每个正式声明支持的发行版都必须使用实际面向它发布的同一候选产物完成验收。三个 zip 分别构建、运行完整测试并独立放行；一个产物或一个现代系统的结果不能替代另一个目标的证据。模拟器或兼容层可以提前发现问题，不能作为唯一发布证据。

## 方案比较

### 方案一：以端到端和真实模型为中心

少量单元测试，主要通过真实模型在真实工作区执行任务验证。它贴近用户体验，但慢、昂贵、难复现；一旦失败，很难区分模型波动、协议问题、平台问题还是状态机错误。它也无法系统覆盖崩溃提交点，不适合作为基础方案。

### 方案二：分层测试金字塔

以大量纯 Lua 单元和端口契约为底层，上面增加故障注入、少量脚本化端到端、真实模型评估和平台验收。它容易理解、工具生态成熟，但如果只按模块组织，可能遗漏跨系统的 durable event 与用户承诺。

### 方案三：契约/事件轨迹驱动的分层证据（推荐候选）

保留方案二的层次，同时以设计 ID、领域不变量和事件轨迹作为贯穿所有层的测试 oracle。每个 P0 行为至少映射到一个正常场景、一个关键失败场景和所需平台证据；同一场景可以先由确定性替身运行，再用真实模型和发行包提升可信度。

优点是能够直接回答“哪个承诺已有何种证据”，也适合 AgentLoop 的 typed outcome 和上下文 replay；代价是场景格式、事件 matcher、夹具版本和证据清单需要从设计阶段维护。

## 替身与场景格式候选边界

- 替身只实现公开端口契约，不允许测试直接改 AgentLoop 内部状态。
- 模型脚本表达规范化流事件、错误和时间点；provider 专有录制物放在协议层测试。
- 虚拟文件系统适合大多数逻辑测试，但原子替换、锁和 flush 必须在真实文件系统另测。
- 虚拟时钟控制超时与退避；墙上时间只用于显示，不参与结果稳定性。
- 场景夹具包含 schema version、初始工作区、配置/权限快照、输入、事件计划、预期 outcome、允许的 diff 和禁止副作用。
- golden 文件更新必须可审阅，不能用“全部重录”掩盖语义变化。

是否自研极小 Lua 测试运行器、选用兼容 Lua 5.5 的现成框架，或由 luainstaller 提供测试入口，属于实现契约轮；此处不先决定。

## 旧 Windows / Linux 约束

- 所有确定性核心测试必须在 Lua 5.5 语言级别运行，不依赖仅在 LuaJIT、Lua 5.1/5.4 或某一宿主 shell 存在的行为。
- 平台脚本不得假设 PowerShell、新版 `cmd.exe` 特性、bash 专有扩展、systemd、容器或现代证书库必然存在。
- Win32 x86 的地址空间和旧机器内存要求测试超大上下文、工具输出和并发时有保守上限，不能用开发机资源掩盖无界增长；Win64 必须使用自己的 x86_64 原生组件和候选包重新验证，不能沿用 Win32 结论。
- 时间分辨率、文件锁、rename/replace、flush、路径大小写、短文件名和代码页均按能力契约测试，不能把 Linux 结果外推到 Windows。
- 测试产物和报告使用可移植编码与文件名；终端不可显示 Unicode 时仍能通过稳定 ASCII 状态和错误 ID 判断结果。
- 真实平台机必须验证发布目录本身，不从父目录、开发仓库或系统 PATH 偷用依赖。

## 失败分类与证据保存

候选失败类别：

- `assertion`：确定性结果违反契约。
- `fixture`：场景或替身本身无效，不能计为产品通过/失败。
- `infrastructure`：测试机、网络或 provider 不可用；必须与产品失败分开。
- `stochastic_regression`：真实模型指标越过确认阈值。
- `platform_regression`：正式产物在声明平台失败。
- `evidence_missing`：要求的日志、事件、diff 或版本信息缺失，无法证明结果。

每次正式验收必须保存：源码提交、构建/luainstaller 标识、zip SHA-256、component/license manifest、SBOM、OS/架构、测试清单版本、配置的非秘密摘要、开始结束时间、逐场景结果、诊断附件和最终放行结论。三个 zip 分别形成证据集；缺少要求的证据按 `evidence_missing` 处理并阻断对应包。保留期限、存放位置和是否进入仓库仍待决定。

## 待确认的验收问题

- 哪些 P0 不变量属于“任何环境一次失败即阻断”，哪些 Agent 质量指标使用统计阈值？
- 脚本化模型场景能否作为完整 Agent Loop 的正式发布门槛，真实模型评估是否也必须阻断发布？
- 网络/provider 测试失败时，如何区分基础设施故障与产品回归，允许重试多少次？
- 故障注入需要覆盖哪些 durable 屏障；哪些必须通过杀进程/断电近似验证，哪些端口替身足够？
- Agent 场景是否允许修改真实 Git 仓库；怎样保证并行测试、临时目录和失败清理不接触用户工作区？
- 平台证据由人工确认、自动采集还是两者结合；缺失证据是否等同失败？
- 性能基线按最低配置机器、虚拟机还是预算值定义；回归容忍度如何设置？

## 建议讨论顺序

1. 先确认测试判定权：结构化状态/事件/副作用证据与自然语言分别能决定什么。
2. 确认哪些确定性测试、安全不变量和真实平台失败必然阻断发布。
3. 定义四层各自的最小闭环，以及模拟物不能替代的真实边界。
4. 确认场景夹具、事件 trace、workspace diff 和结束报告的共同格式。
5. 枚举 AgentLoop、上下文、工具、权限和压缩的故障注入点。
6. 决定真实模型评估的模型版本、重复次数、指标、阈值和人工复核。
7. 最后确认平台矩阵、执行环境、证据保留、CI/人工分工和发布门槛。

## 当前讨论入口

先决定“发布判定以什么为权威”：推荐由确定性的 typed outcome、durable event、不允许的副作用和验证证据构成硬门槛；真实模型任务质量作为独立统计门槛或观察指标，不能反向宽恕硬不变量失败。确认这一点后，才能为每个子系统写不会被模型波动干扰的验收条件。
