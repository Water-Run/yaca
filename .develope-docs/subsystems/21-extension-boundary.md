# 21 扩展边界与未来兼容

状态：候选，尚未确认

## 为什么现在讨论扩展边界

即使 v0.1 不实现扩展生态，AgentLoop 事件、工具 schema、权限记录、配置命名和上下文恢复也可能因为未来的 MCP、插件、hook、skills、自定义工具或子 Agent 而产生长期约束。当前目标不是提前搭建插件平台，而是决定哪些能力正式支持、哪些只保留窄边界、哪些明确排除，避免核心同时出现“假装可扩展”和“永远只能单一实现”两种问题。

本文件承接 `PROD-04`、`PROD-11`、`TOOL-14`、`TOOL-16`、`INSTR-*`、`SAFE-*`、`LOOP-11`、`LOOP-21`、`LOOP-23` 与 `CFG-08`。所有结论目前都是推荐候选，不是 v0.1 已确认范围。

## 职责

- 为各类扩展给出不混淆的术语、信任等级、生命周期和所有权。
- 决定 v0.1 的支持/预留/排除矩阵，并记录重新评估条件。
- 定义未来公开边界需要携带的版本、capability、权限、身份和错误信息。
- 保证扩展不能绕过核心权限、上下文提交、工具配对、取消和预算不变量。
- 规定缺失、损坏、版本不兼容或被撤销的扩展如何影响配置、会话恢复和用户数据。

## 不属于本系统的内容

- 内置工具的具体行为由 07 号系统定义；本系统只决定第三方如何进入同一工具边界。
- 项目/用户指令的发现、优先级和不可信标记属于 `INSTR-*`；只有可复用的声明式指令包才可能称为 skill。
- 审批规则和授权生命周期由 08 号系统拥有，扩展只能声明请求，不能决定 allow。
- AgentLoop 仍拥有 turn、调度、取消和终止；hook、MCP server 或子 Agent 不能另建一套隐藏循环。
- 安装器和升级器由 16 号系统拥有；扩展包管理只在正式进入产品范围后设计。

## 术语与能力边界

### 自定义工具

用户或第三方提供的新工具定义与执行体，通过统一 Tool Descriptor、参数 schema、结果 envelope 和权限元数据参与调度。它不等于“任意 shell 命令的别名”，也不应天然获得工作区、网络或秘密访问权。

### MCP

一种外部工具/资源/提示服务协议适配器。MCP server 是独立信任主体；即使协议能枚举工具，每次实际动作仍必须转换成 yaca 的 capability 与权限请求。协议支持不等于允许任意 server 自动启动。

### 插件

可向 yaca 注册一种或多种能力的安装单元。若允许插件代码在主 Lua 进程内执行，它将天然接触核心内存、文件 API 和秘密，难以被 08 号权限系统真实约束；因此“插件”不能只被当作更方便的自定义工具。

### Hook

在确定生命周期点接收事件的观察者或受限控制器。观察 hook 只能取得经分类/脱敏的事件；控制 hook 只能返回版本化、枚举化结果，例如 continue、wait 或 deny，不能任意修改 AgentLoop 内部表。

### Skill

候选定义是带 manifest 的声明式指令/工作流资源，可包含文本、模板和静态引用，但不因名为 skill 自动获得代码执行或工具权限。普通项目指令仍按 `INSTR-*` 处理；是否把可复用包正式命名为 skill 需要单独决定。

### 子 Agent / 后台执行者

拥有独立执行身份、上下文视图和预算，但受父任务、权限和取消关系约束的运行者。这是执行拓扑能力，不只是插件类型；未来即使由扩展提供，也必须由 AgentLoop 分配 actor/executor ID 并统一收口。

## v0.1 范围矩阵：推荐候选

| 能力 | v0.1 推荐状态 | 当前保留的边界 | 明确不承诺 |
| --- | --- | --- | --- |
| 内置工具 | 支持 | 统一 descriptor、结果、capability 和版本 | 第三方注册 |
| 自定义工具 | 排除运行支持 | 不让调度器假设工具必为硬编码；保留来源 ID | 安装、发现、执行任意第三方工具 |
| MCP | 排除运行支持 | 工具层可由未来 transport adapter 提供 descriptor/result | MCP client、server 管理、协议兼容版本 |
| 插件 | 排除 | 配置、事件和工具使用命名空间/来源 ID | 公共 Lua API、ABI、包管理或热加载 |
| 用户 hook | 排除 | 核心内部生命周期点使用 typed outcome，不暴露可变内部对象 | 运行 shell/Lua hook、修改 prompt 或越权放行 |
| Skills | 不以扩展协议名义支持 | `INSTR-*` 保持来源、作用域、优先级和快照；未来可加 manifest | skill 市场、依赖解析、脚本执行 |
| 子 Agent | 排除 | 关键事件、operation、预算和权限记录避免依赖界面文案；是否提前加入 executor ID 另议 | 并行/后台 Agent、委派协议和自动权限继承 |

“预留”只表示当前结构不故意堵死已知需求，不承诺未来版本兼容，也不要求现在实现空壳 loader、假 MCP client 或无消费者的抽象层。

## 方案比较

### 方案一：封闭核心，只保留语义接缝（推荐候选）

v0.1 只装载随包的内置工具、内部 hook 和内置指令机制；不执行第三方代码或协议 server。现在只把工具来源、事件身份、权限请求、配置命名和结果 envelope 设计为不依赖某个内置实现。

优点是首版安全面、测试矩阵、打包体积和旧系统依赖最小，可以先稳定 AgentLoop 与上下文事实模型；代价是早期用户不能自行接入工具，未来第一次开放协议时仍需正式版本设计。

### 方案二：首版开放仅进程外工具协议

允许经用户显式配置的自定义工具，必要时实现一个受限 MCP 子集；所有第三方执行体在独立进程，通过 stdio 消息交换，由核心做 schema 校验、超时、输出限制和权限审批。

它比进程内插件更容易隔离崩溃和版本，但“进程外”并不自动形成 sandbox：外部程序仍拥有启动用户的 OS 权限。它还会把发现、握手、生命周期、编码、取消、日志和协议兼容全部拉入 v0.1 测试范围。

### 方案三：首版开放进程内 Lua 插件与完整 hooks

插件直接 `require` 核心模块、注册工具或修改 loop/prompt，开发体验最灵活，但几乎无法阻止它绕过权限、读取秘密、破坏上下文或依赖内部实现。Lua 源级 API 也会过早冻结重构边界，不建议用于 v0.1。

推荐先采用方案一。若项目负责人认为自定义工具是首个完整闭环的必要条件，则收窄到方案二，只开放进程外、显式配置、默认未信任的工具；仍不同时开放进程内插件、任意 hook 和子 Agent。

## 权限与信任不变量候选

1. 扩展 manifest 只能声明所需 capability；08 号权限系统按规范化参数和当前信任状态独立判定，扩展不能授予自己权限。
2. 安装/启用、启动进程、读取项目/用户数据、联网和执行具体工具是不同授权时点，不能用一次模糊“信任插件”全部放行。
3. 未知 capability、未知安全关键字段或更高的主协议版本默认拒绝；不能悄悄忽略后继续执行。
4. 第三方返回的文字、资源和 prompt 一律是不可信数据，不能提升为 system/product 指令。
5. 每个 tool call 仍必须产生真实或合成结果；扩展崩溃、超时、取消和断连不能留下孤立调用。
6. 扩展看见的事件和日志遵守 `PROD-08` 数据分类；秘密使用显式引用/句柄时，不把原值写入 manifest、参数、错误或上下文。
7. 控制类 hook 的返回值必须有限、可审计、可超时并计入循环预算；hook 不能递归触发同一 hook 形成隐藏循环。
8. 子 Agent 不继承“更大权限”；委派权限至多是父作用域与自身授权的交集，并具有独立预算与取消关系。

在没有 OS sandbox 的 XP 和旧 Linux 上，策略审批只能约束 yaca 通过自身工具边界发起的动作，不能声称隔离任意第三方进程或进程内 Lua 插件。

## 版本与身份边界候选

未来若开放扩展，至少需要区分：

- `extension_id` 与来源/安装实例，避免显示名或目录名承担身份。
- manifest/schema 版本、协议版本与每项 capability 版本，避免一个数字同时代表全部兼容性。
- tool 的稳定全名、参数 schema 版本、结果 envelope 版本和调度 metadata。
- hook point 名称、输入事件版本、允许的返回类型和超时/失败策略。
- session、turn、call、operation 与可选 executor/actor 的关联，保证恢复时能指出原执行者。
- 配置命名空间、状态目录、缓存目录和秘密引用，防止两个扩展覆盖同一 key 或文件。

首版内部结构可以变化，不应宣传为公共 API。只有某项能力正式支持后，才为其声明兼容窗口、弃用流程和迁移规则；“字段存在于上下文日志”本身不等于第三方可依赖的稳定协议。

## 生命周期候选

未来完整扩展至少经历：发现、检查来源、解析 manifest、兼容性判断、用户启用、能力注册、按需启动、健康检查、调用/取消、停止、升级/禁用和卸载。每一步都必须有 typed failure，不能把所有问题显示成“工具失败”。

恢复旧会话时还要处理：

- 原扩展未安装、已禁用或版本不兼容。
- tool schema 已变化，历史调用只能查看不能重放。
- 外部进程上次崩溃时副作用是否已经发生但结果未知。
- hook/skill 内容变化，旧 turn 的实际指令快照是否仍可审计。
- 子 Agent 曾处于运行、待批准或取消中，启动时如何确定性收口。

推荐默认只读展示历史，禁止自动重放外部副作用；要继续会话时重新解析当前能力并向用户说明缺失项。

## 旧 Windows / Linux 约束

- 不把 Unix domain socket、现代 Windows named pipe API、文件权限位或 fork 作为唯一 IPC/隔离基础；若未来开放进程外协议，优先评估结构化 stdio 加独立 stderr 的最小共同能力。
- 所有协议字节应明确 UTF-8；XP 控制台代码页只在 TUI 边界转换，不能污染工具参数和持久事件。
- 子进程启动、引号、环境变量、取消和进程树清理由 02 号系统统一处理，扩展不能自带另一套 shell 拼接规则。
- MCP server 常见运行时、TLS 和依赖未必支持 XP/CentOS 7；正式支持某种 server 前必须把其 runtime 一同纳入各平台发行与验收矩阵。
- 进程内 Lua 扩展不得假设可加载任意 native module；Windows 只允许 x86，Linux 只允许 x86_64，且 C ABI/CRT 差异会扩大支持面。
- 旧机器资源较小，扩展数量、握手时间、并发进程、消息大小、输出和内存都必须有硬上限。
- 无法建立真实隔离时必须向用户准确表述风险，不把“进程外”或“需要审批”宣传成 sandbox。

## 失败与验收问题

### 必须设计的失败

- 重复 tool 名、伪装内置来源、manifest 损坏或版本过高。
- 外部工具启动失败、握手超时、stdout 混入日志、消息过大、畸形编码或无限输出。
- 工具已造成副作用后断连，结果未知且恢复时禁止静默重试。
- hook 超时、抛错、返回未知动作、递归触发或相互矛盾。
- skill 引用丢失、内容变化、包含伪装高优先级指令或越权工具要求。
- 插件/工具升级、禁用或卸载后恢复旧会话。
- 子 Agent 丢失心跳、父 turn 取消、预算耗尽、权限请求悬空或结果晚到。
- 扩展日志、错误和诊断包意外包含 token、秘密、文件正文或未脱敏路径。

### 正式开放任一能力前的最低验收候选

- 未安装任何扩展时，核心行为、启动时间和上下文格式不受影响。
- 不兼容或恶意输入只能使该扩展/调用失败，不能绕过权限或损坏 session 事实源。
- 取消、超时、崩溃和恢复后 tool call/result 与 turn terminal outcome 保持完整。
- 启用/禁用/升级的配置来源、实际版本与权限范围可查看、可审计。
- 在每个正式支持平台使用发行包执行正常、拒绝、断连、超限和恢复场景。
- 扩展缺失时旧历史可安全查看；继续运行不会自动重复未知副作用。

## 建议讨论顺序

1. 先确认 `PROD-11`：六类能力在 v0.1 分别是正式支持、仅保留语义接缝还是明确排除。
2. 为每个进入 v0.1 的能力确定信任模型：声明式数据、进程外代码或进程内代码。
3. 确认扩展永远不能绕过的权限、事件、工具配对、取消、预算和持久化不变量。
4. 确认 tool/hook/skill/sub-Agent 的身份、版本、命名空间与恢复关系。
5. 定义发现、启用、升级、禁用、缺失和不兼容的用户流程。
6. 最后才选择 IPC 编码、manifest 格式、目录布局和具体 MCP 协议版本。

## 当前讨论入口

先确认 v0.1 是否采用“封闭核心、预留语义接缝”的范围：只正式支持内置工具与内部生命周期点；MCP、自定义工具、用户 hook、插件、skill 包和子 Agent 都不开放运行支持。若自定义工具被认为是首版不可缺少的产品能力，再单独讨论一个受限的进程外协议，而不是把所有扩展类型一起引入。
