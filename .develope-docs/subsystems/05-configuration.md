# 05 配置与模型注册表

状态：候选

## 职责

加载默认模板和用户配置，验证 Network、Exec、Permission、Context、Tui、Model、AgentLoop 等配置区域，产生只读的运行时配置快照，并支持受控更新与重置。

## 边界

- INI 语法由 04 号子系统处理。
- 交互式配置界面由 CLI/TUI 调用本系统提供的应用服务。
- “选择、重命名、删除上下文，并按目录树访问/搜索”的交互界面是 11 号上下文浏览器；本系统的配置编辑器只浏览配置 schema 与配置值，不能修改 `CONTEXT` 树。
- 模型协议请求由 06 号子系统处理。

## 设计要求

- 明确缺失、无效、未知字段的处理策略。
- API key 属于秘密字段，展示、日志和导出必须脱敏。
- 文件顺序是否继续表示默认模型/权限，需要形成稳定契约。
- 配置更新应原子写入并保留可恢复备份。

## 现有配置草案审计

`src/_CONFIG_.ini` 已经列出很多字段，但“字段多”不等于配置系统完整。当前实际形态是一个全量用户 INI：

| 区域 | 已有草案 | 主要缺口 |
| --- | --- | --- |
| Network | 代理、stunnel、重试次数与延迟 | CA、分阶段超时、流式、重试分类、秘密传递 |
| Exec | 总超时、输出大小 | 取消、进程树、编码、环境、逐工具限制 |
| Permission | 当前模板仍有四个命名预设及 allow/confirm/regex | `Cautious` 已决定移出权限组；仍缺动作分类、授权作用域、项目信任、审计与迁移 |
| Context | 自动跳目录、自动命名、压缩阈值 | 存储格式、保留/配额、备份、删除、迁移 |
| Tui | 启动检查、性能检查、点命令补全 | plain/basic 模式、颜色覆盖、编码、流式、样式与无 TTY 行为 |
| Model.* | endpoint、key、模型 ID、窗口和 prompt | provider/model 分离、显式默认、能力声明、秘密复用与协议扩展 |
| AgentLoop | 当前模板没有对应区域 | 终止评估器、循环预算、忙时输入和恢复策略 |

跨 section 还缺少：

- `ConfigVersion` 和可回滚迁移契约。
- 内置默认、用户、项目、环境、命令行和会话覆盖的层级与来源显示。
- 配置与 secrets 的分离规则。
- 显式默认模型/权限；当前依赖 section 文件顺序。
- 未知/废弃字段的往返、警告与拒绝策略。
- 同时手工编辑和交互式更新时的锁、冲突检测与备份。

`Model.*` 当前把 provider、模型实例和凭据合成一个对象。同一 provider 下多个模型会复制 endpoint/key，增加秘密漂移和修改成本，是否拆分必须先决定。

现有公开描述本身还有两处冲突，必须在设计阶段消除：README 说配置“注释丰富、可以手工编辑”，`_CONFIG_.ini` 文件头却写着禁止手工编辑；README 提供 `--set-default-model` / `--set-default-permission`，模板却又规定默认项完全由 section 顺序决定。后续选择任一方案时都要同时修改配置契约和公开说明，不能长期保留两套真相。

## 已确认的跨系统配置项：使用终止评估器

面向用户的名称确认采用“使用终止评估器”。为便于设计文档引用，暂记逻辑键 `UseTerminationEvaluator`；这不提前决定它最终属于哪个 INI section，也不提前确定模板中的精确拼写。

该项是布尔开关：

- 关闭时，AgentLoop 接受主模型的正常终止意图。
- 开启时，主模型提出终止后，系统单独发起一次模型请求判断是否允许终止。

尚未确认的配置责任包括：默认值、用户/项目/会话哪一层可修改、是否允许 turn 中热更新、何时冻结有效值、怎样显示来源，以及评估器使用当前模型还是单独模型引用。无论以后选择何种生效时点，都必须避免同一个终止意图在评估过程中先后采用两套开关值。评估 Prompt、上下文和 verdict 格式属于模型层；拒绝、失败和循环上限属于 AgentLoop，不由布尔开关隐式决定。

## 已确认的跨系统配置项：DoubleCheck 与 `.cautious`

`Cautious` 不再作为独立 Permission profile。`DoubleCheck` 改为谨慎复核的默认配置总开关；`.cautious` 只产生当前会话的覆盖值，不重排或切换权限组，也不重写用户默认配置。

会话覆盖写入当前上下文 XML 的会话参数元数据。加载上下文时，配置系统需要区分“用户默认值”“会话覆盖值”和“最终有效值”，但具体 XML 字段、覆盖值缺失/损坏时的回退，以及 `DoubleCheck` 统辖哪些复核子能力尚未确认。

## 配置层级总体方案

### A. 内置默认 + 单一用户配置（推荐作为 v0.1 起点）

项目只读取安装内置默认和一个用户配置文件；命令行/会话覆盖只在内存中生效。仓库不能静默改变 endpoint、权限或工具行为，旧系统实现与诊断最简单。

代价是不同项目不能保存安全的局部偏好。项目指令可以由独立、受限的工作区指令机制承担，不必等同于项目配置。

### B. 增加受限项目配置

允许项目文件只覆盖模型选择、显示和上下文偏好等白名单字段；第一次使用项目配置时显示来源并要求信任。危险字段仍只能来自用户层。

它改善多项目体验，但必须先设计规范路径、信任失效、合并、未知字段和陌生仓库安全。

### C. 完整多层配置

内置、系统、用户、项目、profile、环境、CLI 和会话全部参加合并。表达力最强，但配置来源、删除语义、命名组合并和诊断复杂度很高，不适合作为当前默认。

## 后续必须分别讨论

1. 配置层与项目配置的信任边界。
2. secrets 存储及文件权限不足时的行为。
3. provider、model、credential 的数据模型。
4. 显式默认项与命名组顺序语义。
5. schema 版本、未知项、迁移和降级。
6. 完整 section/字段清单及每项行为来源。
7. `DoubleCheck` 的复核范围及其与 `UseTerminationEvaluator` 的父子关系。
8. 终止评估器的默认值、作用域、模型引用与冻结时机。
9. 原子更新、备份、冲突和恢复。
10. TUI/CLI 编辑器如何显示默认值、会话覆盖和最终有效值并脱敏。

## 当前讨论入口

先决定 v0.1 是否存在项目级配置，以及项目级配置能否改变任何安全相关行为。这个结论会决定合并、信任和 secrets 设计；未知字段策略排在其后。
