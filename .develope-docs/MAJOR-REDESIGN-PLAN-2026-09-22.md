## 0. 与原版的实际差异

负责人进一步指出：“其实现在除了内置工具外和原来的差别应该不大”。
核对改动前 README 与当前实现，原版已经是通用、单 Agent、终端交互、便携、兼容
旧系统的产品。它已有文件/命令工具、模型适配、TLS/CA、权限、历史、压缩与恢复机制。
**本轮是功能增量与兼容性收尾，产品定位和主体架构延续原版。**

| 项目 | 原版 | 本轮实际变化 |
| --- | --- | --- |
| 定位与核心 | 通用 Agent；C/Lua、串行工具、现有 Session/Runtime | 保持，不重新设计产品或 AgentLoop |
| Lua | 内嵌 Lua VM 用于运行 yaca | 开放 yaca 自身内嵌解释器入口；复用现有执行机制，不另发 Lua 程序 |
| tools | 没有正式的可选工具携带/说明约定 | 可按环境放 Python、SSH 等，给 Agent 位置与用法；不要求安装或注册 |
| 开箱使用 | 已有便携包、配置、自检、网络与终端实现 | 修复直接 SSH 的 TtyRequired，衔接首次配置，补旧环境真实验证 |
| 鲁棒性 | 已有预算、取消、重试、持久化与恢复 | 对已发现的容量、编码、大文件等问题逐项复现、按需要补齐 |

上一版将新增能力、既有缺口和架构候选一并列为“大改”，扩大了必做范围。
后文按以下规则执行：Lua 与可选 tools 为明确增量；兼容性问题按证据修补；
onedir 候选已撤回；exec 新 schema、改默认审查、拆分 main 和数据格式迁移均非前置条件。
优先保留当前打包方式、公共接口、默认值和历史格式；只有具体缺陷要求时才采用候选。
F0--F6 是工作分类，不要求每一类都引入机制变更或先完成一轮全面规格重写。

## 1. 本轮交付目标

交付一个简单、鲁棒、便携的通用 Agent，在现代和受支持的旧设备上都容易使用。
程序目录可以位于本地磁盘、服务器或 U 盘；执行 `./yaca.exe`、完成必要的首次模型
配置后，就能处理代码、文件、数据、自动化和问题辅助任务。
网络不可用时仍能访问本地配置、状态、自检和历史。
预配置包可以免去首次模型输入；公共包没有 Key，也不附带离线大模型。

定位按负责人补充修正：U 盘上的旧设备排障是典型场景；通用 Agent 是产品本身，
老设备高度兼容与开箱即用是核心特性。必带的 Agent 工具是同版本 Lua 解释器；
`tools/` 可选，Python、SSH 等按需要打包，只把可用性与用法告诉 Agent。

下一轮围绕代码修改与验证、文件/数据处理、脚本自动化、环境问题辅助四类完整任务
验收，涵盖短任务和多轮任务，走真实启动、模型、工具、落盘、退出/恢复链路。
本轮不增多日自主开发调度、并行 Agent、后台服务或插件生态；这不限制用户任务种类。

| 处理 | 内容 | 理由 |
| --- | --- | --- |
| 保留 | C/Lua 基础、串行执行、双模型协议、权限、intent/result、XML 原子发布、取消收尾 | 已有实现和回归，承担不可重复执行等关键保证 |
| 修补/补充 | 已复现的启动问题、Lua 调用、可选工具说明及验证中暴露的缺口 | 在原实现上达到既定可用性目标 |
| 按证据优化 | 重复逻辑、容量边界、大文件、编码、无效模型往返 | 先确认影响，再做局部改动，不以重构本身验收 |
| 停止沿用 | 固定五项根目录、默认围绕仓库开发的引导、用单 exe 外观评价便携性 | 与本次方向冲突 |
| 暂缓 | 通用 artifact 库、WAL/SQLite 历史重写、多 workspace、session 分支、自动更新 | 优先证明现有执行与恢复闭环，不提前扩充基础设施 |

已有 queue/side 等能力与交互保持兼容，不因本次定位说明而重排或删除。
不另写一个 Agent 框架，也不要求先完成全面拆文件才能修复启动问题。

## 2. 实施路径与条件性候选

### 2.1 一个内嵌核心，三个发行版本

按负责人最新要求，每个平台发行 clean、std、full 三档；full 为开发工具箱。
同平台三档使用同一份 yaca 二进制，仅 tools 组合不同；原三个目标对应九个发行物。
具体默认版本、平台差异、来源与待验收项见
[发行分档与工具清单](../release/TOOL-BUNDLES.md)。

```text
clean/                       std/ 与 full/
  yaca.exe                     yaca.exe       与 clean 核心哈希相同
                               tools/          按版本携带
```

Linux 对应为 yaca。干净运行包只有程序文件；Lua、核心网络与解析依赖均自包含，
不旁置 lua.exe、Lua DLL 或要求 tools 存在。运行后生成相邻 __yaca__ 的原规则保持。
许可、源码与说明按发行附件及内嵌可访问资料交付，不为单文件外观略去交付义务。
此前 onedir/独立 Lua 文件的候选布局撤回，不再作为本轮方案。

std 默认 Python 2.7、SSH/SCP/SFTP、curl、7-Zip；full 增加 Git、Python 3、
C/C++ 开发工具链与 SQLite/jq/文本工具。工具按目标系统选版本，核心不依赖这些附加项。

### 2.2 解释器入口使用 yaca 内部的 Lua

建议给同一 yaca 增加解释器模式，例如 `yaca.exe --lua script.lua`、
`yaca.exe --lua -e "print(42)"`、`yaca.exe --lua -`；语法仍须实现及同步 CLI 契约。
Agent 通过现有 exec 启动同一 yaca 的新进程，由既有机制管理输出、退出、超时和取消。
这个进程使用嵌在 yaca 中的同版本 Lua；不需要第二个解释器文件，也不在主 Agent
持有 Context/Key 的 Lua 状态里执行模型脚本。

解释器模式早于聊天配置/TTY/Context 初始化，不依赖模型配置或 tools，不递归启动
AgentLoop。保持 Shell 权限与普通进程能力；内嵌不代表沙箱或免审批。
先复用 exec，不为 Python、SSH 等各建一个 Tool，也不先引入 program/argv 新 schema。
Lua 完整版本取核心同一锁定输入，当前为 5.5.1，通过解释器版本入口核对。

可选 tools 的说明只提供名称、版本、实际位置、用途和用法；不强制注册/安装，
不在发现时执行程序或联网。官方 std/full 具有明确清单，用户仍能自行增删，
移走整个 tools 不影响核心及内嵌 Lua。系统工具与随包工具分别标明来源。
开发工具的 PATH、库、头文件环境只对相应子进程设置，不修改宿主环境。

### 2.3 统一执行预算与持久化容量

当前源码把 Context 限为 256 个事件、1 MiB XML，另有 64 KiB 单字段限制；Runtime
却允许 256 次工具调用、16 MiB result 预算。事件数不等于工具次数，模型压缩也不会
删除原始事实。不能靠增加某一个数值解决这组约束。

先为当前上限交叉边界建立复现用例，复用现有接纳与预算机制补结果/终态预留。
不要直接引入独立的预算子系统；仅当局部检查无法保证一致性时，再抽取统一规则。
检查覆盖以下维度：

- 模型输入窗口、输出预留、单次/整轮请求与等待预算。
- 原始输出采集、解码文本、工具结果投影和序列化后的字段/文档字节数。
- 当前事实事件数，以及请求、操作、结果、取消/失败终态所需事件和字节。

在接纳用户输入、模型请求或操作前，按对应最大结果形状预留收尾空间；工具输出从
采集端就限制在能投影并落盘的范围，计入 XML 转义/base64 等膨胀。
容量不足时停在操作开始之前，说明原因，提供导出摘要、新开任务的入口；不自动
丢弃历史或拼接多个隐式 Context。已预留的收尾空间不再被其他输出消耗。

逻辑预留不能保证磁盘之后仍可写。真实 I/O 失败继续使用已有 fail-stop/unknown
机制，不宣称操作已回滚。先保留单 XML，测量常用及多轮任务在慢盘上的写入量与发布耗时，
再决定局部序列化优化；模型窗口压缩与历史容量管理分别报告。

### 2.4 面向大文件和旧编码重做读取路径

当前 `read` 即使指定行范围，也先读取整个文件；大于 16 MiB 被拒绝，`search` 会跳过。
当前非 UTF-8 命令输出保守地投影为 base64。两者都不能满足常见旧系统日志诊断。

建议扩展现有 read/search 的版本化参数，实现分块范围读取、尾部读取和有界搜索。
扫描字节、行数、输出、耗时分别设限，返回已观察范围、停止原因和续读位置；
“本次没搜到”与“完整文件没有”必须可区分。超长单行不能撑大内存。
续读绑定文件身份和观察状态；增长、轮转、截断分别报告，不用旧偏移静默接新文件。
大文件观察不伪装成整文件快照，局部摘要的 digest 明确其范围。

编码首批覆盖 UTF-8、带 BOM 的 UTF-16、CP936 和目标机实际 ACP/OEM。
读取允许显式编码，自动检测只采用 BOM 等确定证据；显示可报告有损解码，写回必须
无损且由显式编码决定。native 提供当前代码页事实与严格转换，保留 raw digest、
BOM、CRLF 和文件身份校验。命令输出按声明/观察到的代码页解码，未知则保留字节。
小文件 write/patch 继续整文件 CAS；大日志读取能力不自动扩展为大文件就地修改。

### 2.5 默认交互保持通用、简单、直接

本轮保持 DoubleCheck、自动命名及现有交互的默认值。此前建议默认关闭额外模型
审查/命名，缺少足够实测依据，撤出必做范围。如后续对照任务证明某项额外请求
有明显成本再单独评估；任何默认值变更都要保存旧配置的有效偏好。
权限确认、文件身份复核、执行结果验证与 unknown 处理继续生效。

沿用已有入口，补充 Lua/可选工具说明和必要的配置衔接。启动摘要可包含 OS/位数、
workspace、shell/编码、已验证工具、模型与去凭据路由；不探查无关业务目录。
系统提示围绕用户任务、工具选择、结果验证和能力边界编写，不预设排障流程，
也不假定每个 workspace 都是代码仓库；帮助示例覆盖不同工作负载。
普通启动只查关键依赖与当前数据；全局历史扫描归显式自检/历史入口，
其他 Context 损坏不应阻止在有效目录中新开任务。

### 2.6 终端与网络采用明确的失败出口

F1 首选验证随包兼容桥接自动接入 Cygwin PTY，以已观察的 winpty 控制台成功为起点；
原生 PTY 行式适配是备选验证路线。完成隐藏输入、中文、Ctrl-C、EOF、进程退出和
旧系统 API 证明后只保留必要后端，不把“识别 pipe”当作交互支持完成。
不得依赖机器预装 winpty、临时安装 Cygwin 运行库或新式 ConPTY API；若候选桥接
做不到自包含，转向备选实现并重新验收，不把手工命令作为完成标志。

网络保留随包 curl/Mbed TLS/CA 和现有模型适配器；错误按本地组件、DNS/TCP、代理、
TLS、HTTP、协议、流式阶段归类。路由选择和企业 CA 配置放入同一次启动的可达入口。
有限自动重试只有一个 owner，等待可取消；已发布 canonical event 后不透明重试。
不禁用证书校验、不自动改 HTTP、不把错时钟伪装成 Key 错误。
完整故障矩阵沿用[路线第 5 节](PRODUCT-ROADMAP-2026-09-22.md#5-老环境网络的完整路径)。

## 3. 核心职责和恢复语义

主流程收敛为：接纳并保存输入 → 冻结 turn → 容量接纳 → 模型请求 → 校验响应 →
串行工具的权限/intent/执行/result → 再请求或明确终止。取消先停止新工作，再收拢
已启动进程，最后发布事实并恢复终端。MiniMax 的采样边界、ZCode 的重试边界、
DeepSeek 的取消/发布顺序只取这些局部机制，详见固定提交源码对照。

| owner | 唯一职责 | 不应承担 |
| --- | --- | --- |
| main / 启动装配 | 组件连接、入口路由、首次引导 | 再实现预算、工具终态或 XML 事务 |
| Session / Context | 接纳、容量预留、事实发布、锁与恢复 | 直接执行工具、决定网络重试 |
| Runtime / AgentLoop | turn 状态、冻结预算、下一步和终态 | 文件存储细节、第二套进程 owner |
| Model / Network | 请求投影、流解析、单一有界重试 | 重跑工具、推断操作成功 |
| Tools / Process / native | 身份复核、执行、字节采集、取消与收拢 | 自动恢复业务操作、隐式放宽权限 |

提取模块时每批只移动一种职责；先用状态转换和故障用例锁定行为，再去重。
不为上表增加消息总线、依赖注入框架或通用 workflow 引擎。

| 恢复时的证据 | 用户可见结果与下一步 |
| --- | --- |
| 能证明尚未开始的操作 | 明确未执行；再次执行走新请求/新审批 |
| 已有 intent，没有可信 result | 效果未知；先只读核查现场，再决定新操作；不自动重放 |
| 进程结果观察到，但发布失败 | 保留失败/未知状态；不能把内存观察当持久化成功 |
| 历史审批或未决 review | 展示原状态，重新接纳后取得当次授权，不继承旧审批能力 |
| 压缩中断 | 保留旧模型视图、关闭未决压缩，不删除事实 |
| XML 损坏或文件身份变化 | 提供有证据的 previous 修复/只读导出；失败时不接纳副作用 |
| U 盘换主机、盘符或 workspace | 显示身份差异，要求显式续接/重绑定；不凭同名路径继续 |

恢复入口必须能给出可执行下一步，用户不需要手改 XML。
自动探查仅使用现有权限允许的只读操作，不能为“检查是否成功”重复原修改命令。

## 4. 兼容迁移与回退

| 对象 | 迁移策略 | 回退条件 |
| --- | --- | --- |
| yaca | 整体替换同平台程序；三个分档使用同一核心 | 保留旧 executable 即可回退程序；历史格式兼容另行核对 |
| 可选 tools | 官方选配组件按闭包更新；用户自备内容单独保留，重新生成能力说明 | 可以直接移除，不阻止核心运行；不覆盖用户凭据/配置 |
| INI/默认值 | 先按旧 schema 解析有效值，预览差异，事务保存；新默认只给新配置 | 备份原字节；旧省略值需显式保留，不能悄悄改变审查/权限 |
| XML 历史 | 尽量保持现有格式；确需新事实类型时版本化 reader/writer | 使用旧包及原历史副本，不能承诺旧程序能读新写入 |
| 已结束旧 Context | 优先只读兼容；需要转换则先在独立副本中校验，再显式接入 | 原件不覆盖、不双写；失败保留诊断与原件 |
| 未决操作/损坏历史 | 先执行上表的恢复判定；不靠格式迁移消除 unknown | 只读导出/修复或新任务，不产生重复副作用 |
| USB 路径变化 | 组件相对程序目录定位；workspace 按身份规则显式处理 | 禁止全局字符串替换盘符来“修复”历史 |

本轮优先不改变配置/历史格式。上表是发生不兼容变更时的约束，不是要求先建迁移系统。
只有实际采用了新的 schema，才在对应变更中冻结版本边界与迁移 fixtures。
升级说明覆盖预配置私有包与公开无凭据包，导出诊断不带 Key/代理密码。
无需注册表、系统 PATH、服务或系统证书库改动；只读介质给出复制到可写目录的办法。
回退程序不回退已经发生的业务操作，恢复页面必须保持这个区别。

## 5. 开工顺序和可审阅交付

继续使用 F0--F6，不另建一套相互竞争的任务编号。先顺序完成指定服务器的一条完整
旅程，再扩大平台范围；下面每批都必须产出实际可运行结果及对应证据。

| 工作包 | 本蓝图补充的具体产出 | 退出/回退边界 |
| --- | --- | --- |
| F0 契约增量 | 仅同步本批实际变化：可调用 Lua、可选 tools、相应包允许项与说明；其他接口变更按需同步 | 与旧契约差异可核查；不先重写全套规格，Gate R 关闭 |
| F1 首次可用 | 小型 PTY 证明、配置入口衔接、启动错误处理 | CMD 与 SSH 直接入口通过；不以改打包方式为前置 |
| F2 网络闭环 | 去凭据路由/故障说明、代理/CA 操作入口、有界等待和真实故障证据 | 主机上完成一个模型回答；取消/半截流不制造重复请求效果 |
| F3 Lua 与三档发行 | yaca 内嵌解释器入口、复用 exec、clean/std/full 装配及分平台工具清单 | 无系统解释器、无 tools 时 Lua 可用；选配能力可增减；取消正确 |
| F4 缺口修补 | 先复现容量/恢复边界；按实际任务需要补大文件和编码支持，优先保留格式/接口 | 所修问题有回归证据；容量不足不先执行，unknown 不重放 |

F1 是第一检查点：指定环境直接启动、可配置、可退出。F3 是第二检查点：同一包由
模型调用内置 Lua 完成一次文件/数据任务，tools 为空仍通过。F4 是可用预览：
四类目标任务及恢复全部贯通，不以诊断类任务代替通用能力验收。
F6 才评审正式发行。旧 N13 保留作对照；每批可单独审阅/回退，不同时铺开所有子系统。
