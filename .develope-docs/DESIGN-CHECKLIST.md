# 全产品设计决策清单

更新日期：2026-07-18

状态：首轮盘点完成，待逐项确认

## 用途

本文件列出 yaca 在编码前需要由项目负责人决策的完整主题。它是问题地图，不是已经确认的设计，也不要求一次回答全部问题。

讨论分两轮：

1. **系统契约轮**：先确认用户体验、生命周期、数据语义、状态、失败恢复、安全和旧平台降级。
2. **实现契约轮**：系统契约确认后，再确定接口形状、数据格式、算法、模块布局和测试细节。

参考项目只用于发现成熟实现已经遇到的问题，不自动成为 yaca 的设计结论。每次只深入一个主题，给出方案、取舍与推荐，由项目负责人决策后写入对应子系统文档和 `DECISIONS.md`。

## 优先级

- **P0**：会改变产品行为或后续多个系统边界，必须最先确认。
- **P1**：影响一个子系统的完整契约，在实现计划前确认。
- **P2**：实现和发布细节，可在系统行为稳定后确认。
- **暂缓**：明确不进入 v0.1，但记录重新评估条件。

## 建议讨论主线

1. 产品闭环与 Agent Loop。
2. 上下文的完整历史、恢复、索引与压缩。
3. 工作区指令、工具、改动事务与权限。
4. 配置、秘密、模型注册表与默认项。
5. CLI/TUI 的交互流程和视觉语言。
6. 模型协议、网络、进程、平台和数据格式。
7. 诊断、测试、打包、安装与发布。

这条顺序按用户可感知的机制组织，不代表实现时可以跳过底层依赖。

- **PROD-11 非目标清单**：Web、插件、MCP、语音、图像、远程控制、多 Agent、自动更新等能力在 v0.1 中明确支持、预留或排除哪些？Web 当前按暂缓处理，恢复条件由本项与 `WEB-01` 共同记录。

## 09 Agent Loop 与会话状态机

这是首要设计主题。参考实现只提供问题样本，yaca 仍需按单 Agent、Lua 5.5 和旧系统约束重新选择。

### P0

- **LOOP-01 回合边界**：一次用户输入从哪个 durable 事件开始，到哪个终止事件成为一个 turn；排队输入与同轮 steer 是否开启新 turn？循环次数由 `LOOP-04` 决定。
- **LOOP-02 状态机**：至少需要哪些显式状态，例如待输入、准备、请求模型、流式接收、终止评估、等待批准、执行工具、压缩、重试、取消、完成、失败？
- **LOOP-03 完成与继续（已确认核心方向）**：正常完成由主模型主导；关闭终止评估器时接受主模型终止意图，开启时先单独请求评估。Runtime 仍如实收口取消、硬预算、未完成工具和基础设施错误；评估控制流由 `LOOP-25` 继续确认。
- **LOOP-04 循环预算**：单轮模型请求次数、工具调用数、墙钟时间、token、输出字节和费用分别如何限制？
- **LOOP-05 进展检测**：如何从重复相同工具/参数、ABAB 模式、连续相同答案和状态无变化判断“没有进展”；达到什么程度发警告或产生 stuck 结果？硬预算和压缩循环分别由 `LOOP-04`、`COMP-04` 决定。
- **LOOP-06 用户中途输入**：Agent 工作时的新输入是立即打断、下一步 steer、排队到下一轮，还是由用户显式选择？
- **LOOP-07 业务取消契约**：在模型请求、审批、工具执行、重试和压缩中收到取消后分别进入什么状态；已经发生的副作用和持久化如何呈现？按键、传输和进程树行为分别由 `TUI-06`、`NET-09`、`PROC-03` 定义。
- **LOOP-08 恢复语义**：从最后完整 turn、最后 durable 事件或未完成工具循环恢复时，业务上继续、终止还是等待用户；副作用重放遵守 `TOOL-15`，物理记录修复遵守 `CTX-08`。
- **LOOP-09 验证责任**：有可用验证命令时 Agent 是否必须尝试验证；失败后允许自动修复多少轮？
- **LOOP-10 阻塞转换表**：缺少信息、权限拒绝、危险动作、文件冲突、存储失败和不可恢复错误分别转换为继续、等待用户、取消、部分完成或失败中的哪一种？
- **LOOP-18 计划模式范围**：v0.1 是否支持计划模式；若支持，它如何复用或区别于 `SAFE-05 Readonly`，从计划进入执行是否生成新 turn 与权限快照？
- **LOOP-19 Prompt 装配**：在 `INSTR-01` 至 `INSTR-03` 确定来源、优先级和信任后，AgentLoop 如何装配系统规则、用户输入、工作区指令、压缩摘要与工具结果，并记录实际输入？
- **LOOP-23 执行所有权**：同一 session 是否永远只允许一个 active turn；多个 session 是否并行；模型请求与工具执行的进程级全局上限是什么？
- **LOOP-24 启动收口**：启动时遇到遗留的 running tool、pending approval、retry 或 compaction marker，分别自动转成中断结果、等待用户还是允许受控续跑？
- **LOOP-25 终止评估控制流（部分确认）**：已确认主模型终止后可触发独立评估请求；仍需决定允许/拒绝/无效输出/超时/请求失败分别如何转换，是否在同一 turn 继续，以及评估次数、费用和墙钟上限。

### P1

- **LOOP-11 领域事件模型**：如何把 `MODEL-02` 的 provider 事件转成持久化事实事件与仅供 UI 的增量；事件如何分类、排序、关联 turn/tool ID 并去重？
- **LOOP-12 工具调度**：多个工具调用的顺序、并发资格、结果回送顺序和任一失败后的策略是什么？
- **LOOP-13 工具配对不变量**：任何已接受的调用都必须产生 `TOOL-06` 定义的真实或合成结果，包括失败、拒绝、取消和崩溃恢复，是否作为不可破坏的硬不变量？
- **LOOP-14 整请求重试**：依据 `NET-06` 的错误标记，流开始前、收到部分文本后、收到工具请求后断流时是否允许重启整次模型请求？
- **LOOP-15 turn 冻结**：每个 turn 在何时冻结模型、权限、工具、工作目录和指令；中途配置变化从下一采样、下一 turn 还是新会话生效？持久内容由 `CFG-12` 定义。
- **LOOP-16 流式提交**：文本增量是否立即进入规范历史，还是只在完成事件后提交；断流时部分文本是否保留给用户/模型？
- **LOOP-17 错误归属**：传输、模型、协议、工具、权限、存储和 UI 错误如何决定重试、继续、等待或终止？
- **LOOP-21 后台执行者兼容**：若 `PROD-04` 要求未来兼容后台执行者，当前哪些 ID、事件、锁和权限记录不得假设永远只有单执行者？若明确排除，则本项暂缓。
- **LOOP-22 结束报告**：完成、部分完成、取消、阻塞和失败分别向用户报告哪些改动、验证和未完成项？

## 第一轮完成标准

第一轮不是回答所有实现问题，而是做到：

- 每个 P0 问题都有明确结论，且不存在互相冲突的用户体验承诺。
- 每个子系统能描述正常流程、状态、失败与恢复，不只描述模块名称。
- 配置 schema 中每一项都能追溯到已确认行为，不保留“看起来可能有用”的字段。
- Agent Loop、上下文、权限和 TUI 共享同一套事件与状态语义。
- v0.1 非目标明确，不因参考项目功能丰富而无边界扩张。
