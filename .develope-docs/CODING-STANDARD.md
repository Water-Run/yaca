# 编码规范与注释约束

生效日期：2026-09-23。依据负责人明确要求：文件头使用固定格式；任何函数、元表等均须
完整注释，使用 `--@param`、`--@return` 这类标记，不得遗漏。本规范适用于现有代码和后续修改，
属于实现、Review 和发行验收的共同约束。

## 覆盖范围

仓库维护的产品源码、原生接口、入口、构建与打包脚本、检查器、测试、测试辅助代码、
可执行契约及证明程序全部适用。公开、私有、局部、嵌套、匿名、回调、方法、构造器、
析构器和元方法一视同仁；短函数、空函数、单行函数也必须注明。不能用“内部函数”或
“测试代码”作为免注释理由。

第三方原始源码保留其作者与版权，不能改署 WaterRun；项目自有适配和生成器模板遵守本规范。
构建输出通过其源文件或模板维护注释。作为数据的字符串、负向语法测试输入、JSON、二进制
夹具不插入会改变数据含义的注释；它们的维护代码仍全部适用。

## 文件头

Lua 文件开头统一如下，字段及顺序固定，不使用旧顺序或省略字段：

```lua
--[[
Author: WaterRun
Date: 2026-09-23
File: example.lua
Description: 说明文件负责的行为、边界与主要用途。
]]
```

`Date` 使用实际创建或本次实质更新日期，格式 `YYYY-MM-DD`，不填写未来日期。
`File` 必须与文件名一致；`Description` 必须有具体内容，不能仅重复文件名。
Python、Shell 的 shebang 和必要编码声明可在文件头之前；四个字段改用该语言合法的注释
符号。C/C++ 使用 `/* ... */`，Python/Shell 使用 `#`，PowerShell 使用 `<# ... #>`。
字段、顺序和语义不变，现有第三方许可声明完整保留。

## 每个函数的注释

定义前紧邻放置说明及标记，注释必须逐项对应真实签名和行为：

```lua
-- 读取已经绑定身份的 Context；身份或内容变化时拒绝继续。
--@param path string Context 的绝对路径。
--@param expected_identity table 已接纳的文件身份，不在此函数内修改。
--@return table|nil 校验后的 Context；失败时为 nil。
--@return table|nil 失败时的结构化错误；成功时为 nil。
local function read_context(path, expected_identity)
    -- 实现。
end
```

- 每个形参必须按签名顺序有且只有一个 `@param`，写出名称、类型、含义；可选值说明默认值。
- 变长参数用 `@param ...` 说明元素类型和顺序；方法说明隐含 `self` 的类型及所有权。
- 无形参写 `@param none 无参数。`，无返回值写 `@return nil 无返回值。`，不能靠空白推断。
- 多返回值逐个写 `@return`；成功、失败、取消、部分结果等实际分支分别解释。
- 有抛错、退出进程、写盘、联网、启动子进程、转移句柄所有权或改变调用方对象的行为，
  必须写明。使用 `@error`、`@effect`、`@ownership`，只描述实际存在的行为。
- 匿名函数与回调也紧邻各自定义说明；必要时展开单行表达式。共享的外层说明不能替代
  多个函数各自的参数和返回值注释。
- C/C++ 使用 `@param`、`@return` 等标记的块注释；Python/Shell/PowerShell 使用其原生
  注释符号。Python 可用紧邻定义前的注释或完整 docstring；lambda 同样逐个说明。
- 注释应解释函数的契约和目的，不能用“处理输入”“返回结果”等占位文本凑齐标记。

## 元表、类型与数据结构

每个元表定义须有 `@metatable` 说明名称、所绑定的值、可变性、代理/索引语义与边界。
使用处引用已有定义时明确对应的元表；内联创建元表也必须注释。各元字段用 `@field`
解释含义，元方法另按函数规则完整注释。类、结构体、联合体、枚举及回调接口以 `@class`、
`@struct`、`@enum`、`@callback` 等明确职责、字段、生命周期与约束。

```lua
--@metatable readonly_view 已冻结数据的只读代理；不接受写入，遍历读取原表。
--@field __index table 仅用于读取的原始数据，由创建者持有。
--@field __newindex function 拒绝所有字段写入并抛错。
local readonly_view = {
    __index = source,
    -- 拒绝通过代理修改已经接纳的数据。
    --@param proxy table 接收写入的只读代理。
    --@param key any 尝试写入的键。
    --@param value any 尝试写入的值。
    --@return nil 不正常返回。
    --@error 始终抛出只读对象不可修改错误。
    __newindex = function(proxy, key, value)
        error("read-only value", 2)
    end,
}
```

## 执行与验收

构建机使用 Python 3.13，按 `.tools/comment_check_requirements.txt` 安装固定版本的语法解析器，
执行 `python3.13 .tools/check_code_comments.py --inventory <报告路径>`。检查范围固定为 Git
维护的完整自有源码集合，含尚未暂存的新文件；`--summary-only` 只减少输出，不改变退出码。
解析错误也算失败。此开发检查不增加 yaca 运行时或发行工具包的依赖。

`.tools/run_coding_readiness.sh` 首先运行检查器的反例测试及全仓注释检查，任何缺项都以非零
退出码停止验收。检查器按语法树包含 PowerShell 匿名脚本块、Shell 内直接交给解释器执行的
here-document 和单引号 `-c`/`-e` 代码；内嵌片段沿用外层源文件头，但其中的函数仍逐个注释。
动态生成的源码须同时 Review 其维护模板，不能把可执行模板当普通夹具数据豁免。

1. 以语法结构枚举自有源码中的函数、回调、元表和类型，检查文件头与注释覆盖，包含现有
   未修改文件；不以只检查 diff、固定通过数量或大面积豁免替代全量检查。
2. 检查器报告文件、行号和具体遗漏，以非零退出码阻止遗漏进入验收；检查器自身同样适用。
3. Review 逐项核对注释与实现。结构检查通过只证明覆盖，不能代替语义审核。
4. 注释补全保持运行行为不变；使用语法检查及适当回归验证。行为改变单独说明、验证。
5. 参数、返回值、生命周期或错误语义变化时同步更新注释。旧注释不准确也属于缺陷。

当前正在将此规范应用到整个现有实现；全量覆盖与语义 Review 完成前，不宣称注释验收通过。
